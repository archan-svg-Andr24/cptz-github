Документ написан так, чтобы его понял студент 3 курса, который знает Python и

### Приоритеты

| Метка | Значение |
|---|---|
| 🔴 **Критический** | ломает работу или теряет данные пользователя |
| 🟠 **Серьёзный** | заметно вредит, но обходится |
| 🟡 **Средний** | неудобство или неполное соответствие ТЗ |
| ⚪ **Мелкий** | косметика, документация, долги |

### Важное вступление: почему тесты «зелёные», а баги есть

```
$ .venv\Scripts\python.exe -m pytest -q
537 passed in 19.51s
```

Все 537 автотестов проходят. Это **не значит**, что приложение исправно.

Причина в том, что тесты проверяют **ядро** (`student_planner/core/`) —
арифметику, репозитории, правила. А почти все дефекты ниже живут на стыке
**ядра и интерфейса**: логика написана правильно и даже покрыта тестами, но
из окна её никто не вызывает. Такой разрыв тесты не видят — они дёргают
функции напрямую.

Отсюда практический вывод для вас: **метод `foo()` существует и покрыт
тестом ≠ кнопка в интерфейсе работает**. Половина находок ниже — ровно про это.

## 2. Критические дефекты

### 🔴 Дефект 1. «Сбросить изменения на эту дату» недоступна из интерфейса

**Где:** `student_planner/ui/pages/schedule.py:498`

**Что не так.** В классе страницы расписания есть полноценный метод
`reset_day()`. Он спрашивает подтверждение, считает число записей через
`dry_run=True`, удаляет оверрайды и обновляет экран. Проблема одна: **к нему
не привязана ни одна кнопка**. Метод существует, но вызвать его из окна
невозможно.

**Как проверить.** Откройте файл и найдите все кнопки на странице:

```
$ Select-String -Path 'student_planner\ui\pages\schedule.py' -Pattern 'QPushButton\('
```

В результате будут «Отменить», «Заменить», «Редактировать сетку недели…»,
«Изменить чередование недель…», «‹», «›», «Сегодня», «Добавить занятие…».
Кнопки сброса даты в списке нет. Теперь проверьте, кто вызывает `reset_day`:

```
$ Select-String -Path 'student_planner\ui\pages\schedule.py' -Pattern 'reset_day'
```

Все совпадения — это определение метода и вызовы **внутри** него самого.
Внешних вызовов нет.

**Почему так вышло.** Метод написали, но не дорисовали кнопку в раскладке
страницы. Классическая ситуация при разработке UI: логику вынесли в сервис,
сервис протестировали, а «проводку» от кнопки к методу забыли.

**Чем грозит.** Пользователь не может отменить все правки одного дня разом.
Требование SCH-08 («Сбросить изменения на эту дату» удаляет оверрайды даты с
подтверждением) не выполнено, хотя код для него готов.

**Как чинить.** Добавить в панель управления страницы кнопку и соединить её
сигнал `clicked` с `self.reset_day`. Кнопку разумно держать неактивной, если
у выбранной даты нет оверрайдов — тогда `dry_run` пригодится ещё и для
включения/выключения доступности.

### 🔴 Дефект 2. Настройки → Общие: молчаливая потеря данных

**Где:** `student_planner/ui/pages/settings.py:116` (`GeneralTab.refresh`)

**Что не так.** Вкладка «Общие» содержит четыре текстовых поля: имя, группа,
колледж, домашняя точка. При открытии вкладки `refresh()` заполняет **только
первые два**. Поля колледжа и домашней точки остаются пустыми — их значение
из базы не подставляется. А кнопка «Сохранить» записывает в базу содержимое
всех четырёх полей.

Получается ловушка: поле выглядит пустым, и при сохранении пустота
записывается поверх реального значения.

**Как проверить.** Воспроизводится скриптом на временной базе:

```python
from student_planner.core.settings_service import SettingsService
from student_planner.core.settings_registry import SettingsKeys

s = SettingsService(db)
s.set_many({SettingsKeys.COLLEGE_NAME: "ГБПОУ Колледж связи №54",
            SettingsKeys.HOME_POINT_NAME: "пос. Авсюнино"})
# college = 'ГБПОУ Колледж связи №54' | home = 'пос. Авсюнино'

tab = GeneralTab(db)
tab.refresh()
# поля после refresh(): college = '' | home = ''   <-- пусто!

tab.name_edit.setText("Иванов Иван")   # меняем ТОЛЬКО имя
tab.save()

# college = '' | home = ''   <-- данные потеряны
```

Достаточно поменять имя и нажать «Сохранить» — колледж и домашняя точка
исчезнут.

**Почему так вышло.** В `refresh()` просто не хватает двух строк:

```python
self.college_edit.setText(self.settings.raw(SettingsKeys.COLLEGE_NAME))
self.home_edit.setText(self.settings.raw(SettingsKeys.HOME_POINT_NAME))
```

Их забыли. Это видно по симметрии: имя и группа заполняются, а следующие два
поля той же формы — нет.

**Чем грозит.** Это самый неприятный тип бага — не падение, а **тихая потеря
данных**. Пользователь ничего не заметит, пока не откроет вкладку снова.
Никакой ошибки не покажется, сообщение будет «Сохранено».

**Как чинить.** Дописать две строки в `refresh()`. Полезно также закрыть
ситуацию архитектурно: если экран обещает строиться из реестра настроек
(SET-08), то `refresh()` должен обходить реестр, а не перечислять поля руками.
Тогда подобная асимметрия не возникнет снова.

### 🔴 Дефект 3. Настройки → Транспорт: поле «Начало учёта» невозможно сохранить

**Где:** `student_planner/ui/pages/settings.py:428` и `:453`

**Что не так.** Две строки противоречат друг другу:

```python
# строка 428 — при показе дата форматируется для человека
self.anchor_edit.setText(format_display(anchor) if anchor else "")

# строка 453 — при сохранении текст из поля уходит в базу как есть
SettingsKeys.STRELKA_PERIOD_ANCHOR_DATE: self.anchor_edit.text().strip(),
```

`format_display` превращает дату `2026-10-01` в `01.10.2026`. Валидатор
реестра ждёт строгий формат `ГГГГ-ММ-ДД` и такой строки не принимает.

**Как проверить.** Задайте якорь и нажмите «Сохранить» на вкладке
«Транспорт». Воспроизведено:

```
anchor_edit.text() = '01.10.2026'
сообщение после Сохранить:
  "Ожидается дата в формате ГГГГ-ММ-ДД, получено: '01.10.2026'"
```

**Почему так вышло.** Один и тот же виджет используется как «поле
отображения» и как «поле ввода», но между ними нет обратного преобразования
`parse_display` → ISO. В проекте такой конвертер есть (`dates.parse_display`),
его просто не вызвали.

**Чем грозит.** Дефект хуже, чем кажется. На вкладке «Транспорт» есть ещё
четыре настройки: порог первой ступени, порог предупреждения, способ оплаты
по умолчанию и число поездок до начала учёта. Все они отправляются в
`set_many` **одним словарём**. Если якорь задан, исключение возникает на нём,
и **ни одна** из пяти настроек не сохраняется.

То есть пока поле «Начало учёта» заполнено, изменить тарифные пороги через
эту вкладку нельзя вообще.

**Как чинить.** Хранить в поле ISO-строку, а человеческий вид показывать
через `setPlaceholderText` или отдельную подпись. Либо парсить ввод:

```python
raw = self.anchor_edit.text().strip()
value = dt.to_iso(dt.parse_display(raw)) if raw else ""
```

Но важнее другое: не сохранять пять настроек одной пачкой, если одна из них
может не пройти проверку. Либо валидировать все до записи, либо сохранять по
одной.

### 🔴 Дефект 4. Запуск падает на повреждённой базе вместо сообщения об ошибке

**Где:** `student_planner/core/database.py:253` (`is_initialized`),
`student_planner/app.py:110`

**Что не так.** Если файл `student_planner.db` повреждён (или это вообще не
база SQLite), приложение аварийно завершается вместо того, чтобы показать
понятное окно «База повреждена, восстановите из копии».

Причина — в цепочке вызовов при старте:

```python
def is_initialized(path: Path) -> bool:
    if not Path(path).exists():
        return False
    conn = sqlite3.connect(str(path))
    try:
        return has_table(conn, "settings") and has_table(conn, "transport_rides")
    finally:
        conn.close()
```

`sqlite3.connect` на битом файле ещё не падает, а вот первый же запрос внутри
`has_table` бросает `sqlite3.DatabaseError`. Обработчика здесь нет.

Дальше в `app.main` ловятся только `SchemaVersionError` и `AppError`:

```python
except SchemaVersionError as error:
    ...
except AppError as error:
    ...
```

`sqlite3.DatabaseError` не является ни тем, ни другим и улетает наружу.

**Как проверить.** Положите в `%APPDATA%\StudentPlanner\student_planner.db`
любой мусорный файл и запустите приложение:

```python
from student_planner.app import open_or_create_database
# НЕОБРАБОТАННОЕ исключение: sqlite3.DatabaseError: file is not a database
```

**Почему так вышло — самое интересное.** Защита в проекте **уже написана
правильно**, просто до неё не доходит очередь. В `open_database`, чуть ниже:

```python
except sqlite3.DatabaseError as exc:
    raise DatabaseCorruptedError(
        f"Файл базы данных {target.name} повреждён. Предлагается создать новую базу "
        "или восстановить данные из резервной копии; старый файл не удаляется.",
    ) from exc
```

`DatabaseCorruptedError` — это как раз `AppError`, и `app.main` его поймает и
покажет диалог. Но `open_database` вызывается **после** `is_initialized`, а
`is_initialized` падает раньше. Красивый обработчик недостижим.

Это учебный пример: «обработка ошибки есть» и «обработка ошибки срабатывает»
— разные вещи.

**Чем грозит.** Пользователь с повреждённым файлом БД видит окно аварийного
завершения (или ничего, если запускает через `start.bat` без консоли) вместо
инструкции, что делать. Требование §37.2 «БД повреждена → предложить новую
или восстановить из копии» не выполняется.

Отдельно: в том же сценарии `is_initialized` на файле **чужой** схемы
(валидный SQLite, но без наших таблиц) вернёт `False` — и приложение
молча создаст поверх новую базу. Данные «чужого» файла при этом никуда не
денутся, но пользователь может не понять, что произошло.

**Как чинить.** Обернуть `conn.execute` внутри `is_initialized` в
`try/except sqlite3.DatabaseError` и возвращать `False` либо сразу
поднимать `DatabaseCorruptedError`. Второй вариант честнее: пусть решение
принимает вызывающий код.

### 🔴 Дефект 5. Счётчик «Стрелки» показывает неверный номер при `cnt0 > 0`

**Где:** `student_planner/core/transport_service.py:592`

**Что не так.** Настройка `strelka_initial_ride_count` (`cnt0`) существует
ровно для одного: пользователь говорит приложению «на карте уже засчитано
N поездок в этом периоде». Приложение должно продолжить нумерацию с N+1.

В методе `strella_state()` есть ранний выход для случая «поездок ещё нет»:

```python
if not counted:
    state = self._with_next_ride(state, base, 1, settings, resolver)
    return self._with_warning(state, settings, resolver, base)
```

Обратите внимание на третью позицию — жёстко зашитая единица. `initial_count`
здесь не участвует вообще.

**Как проверить.** Задайте `cnt0 = 5` и дату начала `01.10.2026`, поездок не
создавайте:

```
next_ride_number = 1          (ожидалось 6)
period_start = None
started = False
next_ride_caption = "Поездок ещё не было"
```

**Почему так вышло — и почему это обидно.** Правильный расчёт в проекте
есть. `StrellaPeriodCalculator.resolve()` для того же самого состояния
«учёт не начат» делает так:

```python
if not self.has_rides and self._anchor0 is None:
    number = self.initial_count + 1
    return PeriodState(..., ride_number=number, ..., state=STATE_UNSTARTED)
```

То есть калькулятор умеет, а `strella_state()` в этой ветке калькулятор
**не создаёт** — подставляет константу. Логика продублирована в двух местах,
и копии разошлись.

**Чем грозит.** Прямое нарушение ACC-M-90. Пользователь, у которого в
текущем периоде уже 30 поездок, увидит «следующая поездка №1» и получит
неверную стоимость: до порога `first_limit` (обычно 35) действует первая
ступень, после — вторая, более дешёвая. Приложение посчитает поездку по
первой ступени, хотя должна быть вторая.

Это дефект **денежного** расчёта, а не только подписи.

**Как чинить.** Убрать ранний выход и всегда считать через
`StrellaPeriodCalculator` — он корректно обрабатывает и пустой список
поездок. Это же устранит дублирование логики.

## 3. Серьёзные дефекты

### 🟠 Дефект 6. Бейдж «Счётчик приближённый» не отображается никогда

**Где:** `student_planner/ui/widgets_panel.py:180` (`StrellaWidget.refresh`)

**Что не так.** Поле `approximate` вычисляется в `strella_state()` в трёх
местах (строки 590, 623, 647 `transport_service.py`), но **ни один файл в
`ui/` его не читает**. Проверяется рекурсивным грепом по всему каталогу
интерфейса, включая подкаталог `pages`:

```
$ Get-ChildItem -Recurse -Filter *.py -Path 'student_planner\ui' |
      Select-String -Pattern 'approximate'
(ничего не найдено)
```

Бейдж из списка UI-13 «Счётчик приближённый» отсутствует в интерфейсе
полностью.

**Как проверить.** Откажитесь от шага FIRST-14 при первом запуске (тогда
`cnt0 = 0` и якорь пуст — по ТЗ счётчик считается приближённым до конца
первого периода). Виджет «Стрелка» покажет обычные данные, без пометки.

**Почему так вышло.** Есть ещё и логическое противоречие — два источника
правды считают по-разному:

```python
# transport_service.py:590
approximate=bool(counted)      # True, если поездки ЕСТЬ

# settings_service.py:196
def is_strelka_counter_approximate(self) -> bool:
    return (self.strelka_initial_ride_count() == 0
            and self.raw(SettingsKeys.STRELKA_PERIOD_ANCHOR_DATE) == ""
            and not self.has_any_strelka_ride())
```

Сравним на состоянии «отказ от FIRST-14» (`cnt0 = 0`, якорь пуст). Замерено
на живой базе:

| Поездки есть? | `approximate=bool(counted)` | `is_strelka_counter_approximate()` |
|---|---|---|
| нет | `False` | `True` |
| да | `False` | `False` |

То есть:

- в состоянии «поездок ещё нет» два источника **противоречат** друг другу —
  один говорит «точный», другой «приближённый»;
- в состоянии «поездка появилась» оба дают `False`, хотя по ТЗ счётчик должен
  оставаться приближённым **до конца первого периода**.

Значит правильно не отвечает **ни один** из них: `approximate=bool(counted)`
говорит «приближённый, если поездки есть», что перевёрнуто по смыслу, а
`SettingsService` учитывает только факт отсутствия поездок и не смотрит на
границу первого периода.

Какой из двух считать эталоном, из кода не следует — это и нужно решить.

### 🟠 Дефект 7. Мини-календарь: метки не рисуются, если в дне больше одного события

**Где:** `student_planner/ui/calendar_widget.py:113`

**Что не так.** Одна строка с ошибкой в типе:

```python
kinds = [self._marks.get(value, "")]
...
if "period" in kinds:
    fmt.setBackground(QColor(COLORS["warning_bg"]))
```

`kinds` — это список из **одного элемента**, а элемент — строка. Выражение
`"period" in kinds` проверяет, есть ли среди элементов списка ровно строка
`"period"`. Это не поиск подстроки.

А `MainWindow._refresh_calendar_marks()` склеивает метки через пробел:

```python
self.nav.set_marks({key: " ".join(value) for key, value in marks.items()})
```

То есть в реальном приложении в `kinds` попадёт `"override rides period homework"`.

Проверим разницу:

```python
"period" in ["period"]                          # True  — работает
"period" in ["override rides period homework"]  # False — не работает
```

**Как проверить.** Воспроизведено на живом виджете:

```
ОДНА метка:
  05.10 'period'  -> фон #3a3320   (правильно)

НЕСКОЛЬКО меток:
  07.10 'override rides period homework'
     фон           = #000000        (ожидалось #3a3320)
     подчёркивание = False          (ожидалось True)
```

**Чем грозит.** Подсветка периода и подчёркивание оверрайда пропадают именно
в те дни, где событий больше всего — то есть где они нужнее. Легенда под
календарём обещает «• изменение • поездки • период • задание», но при
нескольких событиях не отображается ничего.

**Как чинить.** Разделить строку на множество:

```python
kinds = set(self._marks.get(value, "").split())
```

и дальше оставить те же проверки `"period" in kinds` — они начнут работать.

Отдельно замечу: метки `rides` и `homework` не влияют на вид вообще, только
на всплывающую подсказку. Если по ТЗ они должны быть видны, это нужно
доделать; если только в подсказке — стоит убрать их из легенды, чтобы не
обещать лишнего.

### 🟠 Дефект 9. Остаток «Стрелки» учитывает будущие пополнения и поездки

**Где:** `student_planner/core/recalculation.py:217` (`wallet_balance`)

**Что не так.** Функция принимает необязательный `until`, но если его не
передали — **фильтра по дате нет вообще**:

```python
topup_sql = "SELECT amount, fee FROM strelka_topups"
ride_sql = "SELECT paid_price FROM transport_rides WHERE payment_method = 'strelka'"
params_top: tuple = ()
params_ride: tuple = ()
if until is not None:
    topup_sql += " WHERE topup_date <= ?"
    ...
```

А `strella_state()` вызывает её без `until`:

```python
balance=wallet_balance(self.db),      # строка 588
```

Значит в «текущий остаток» попадают операции из будущего.

**Как проверить.** Воспроизведено:

```
balance = 75.00
-- добавляем пополнение на 1000 ₽ от 25.12.2026 (будущее) --
balance = 1075.00        <-- текущий остаток вырос на будущие деньги

-- добавляем поездку от 30.11.2026 (будущую) --
balance = 50.00          <-- текущий остаток уменьшился

wallet_balance(db, until=date(2026,10,20)) = 100.00   <-- правильный вариант
```

**Почему так вышло.** По ТЗ ALG-07 остаток считается «по всем датам
`<= ride_date`», то есть всегда относительно какой-то даты. Когда дата не

**Чем грозит.** Пользователь видит завышенный или заниженный остаток.
Особенно заметно, если он заранее внёс крупное пополнение на будущее.

**Как чинить.** В `strella_state()` передавать `until=clock.today()`.
В отчётах REP-09 `until` — это конец периода, там тоже нужно явно
подставлять дату.

### 🟠 Дефект 10. Отчёт «Неделя» не привязан к неделе Пн–Вс

**Где:** `student_planner/core/transport_service.py:129`

**Что не так.**

```python
@classmethod
def for_week(cls, value: date) -> "JournalFilter":
    days = week_dates(value)
    return cls(date_from=days[0], date_to=days[-1])
```

`week_dates(value)` строит семь дней **начиная с переданной даты**, а не с
понедельника. Значит «неделя» — это скользящие семь дней от выбранного числа.

**Как проверить.**

```
для 2026-12-31: 2026-12-31 .. 2027-01-06
для 2027-01-01: 2027-01-01 .. 2027-01-07
для 2027-01-04: 2027-01-04 .. 2027-01-10
```

Ожидалось бы `28.12 — 03.01` для первой строки (неделя, содержащая 31 декабря).

**Почему так вышло.** В проекте есть готовая функция `monday_of()` из
`dates.py` — она используется в других местах (тип недели, границы периодов),
просто не здесь. Похоже на невнимательность при написании метода.

Отдельно показательно: на `for_week` **нет ни одного теста** —
`test_transport_services.py` проверяет только `for_month`. Поэтому баг и
дожил до сдачи.

**Чем грозит.** Отчёты за неделю не совпадают с тем, что пользователь считает
неделей. Суммы «за неделю» будут съезжать на несколько дней.

**Как чинить.** Использовать `monday_of`:

```python
start = monday_of(value)
return cls(date_from=start, date_to=add_days(start, 6))
```

и закрыть тестом на переходе через Новый год.

### 🟠 Дефект 11. Нельзя сменить шаблон поездки на уже подтверждённый день

**Где:** `student_planner/core/trip_service.py:144`

**Что не так.** `plan()` при наличии подтверждения возвращает его набор и
**игнорирует** явно переданные идентификаторы шаблонов:

```python
if confirmation is not None:
    plan.outbound = (self.templates.by_id(confirmation.outbound_template_id) ...)
    plan.return_trip = (self.templates.by_id(confirmation.return_template_id) ...)
    plan.include_outbound = confirmation.include_outbound
    plan.include_return = confirmation.include_return
    return plan            # <-- outbound_template_id не использован

plan.outbound = self._pick_template(Direction.HOME_TO_COLLEGE, weekday, outbound_template_id)
```

Аргументы `outbound_template_id` и `return_template_id` принимаются, но в
этой ветке не читаются.

**Как проверить.** Создайте два шаблона «Вариант А» (`vehicle='22'`) и
«Вариант Б» (`vehicle='35'`). Подтвердите день с А, затем попробуйте
сменить на Б:

```
подтвердили шаблоном А -> поездки: ['22']
confirm(day, outbound_template_id=<Б>) -> поездки: ['22']
                      ^^ ожидалось ['35']
```

**Почему так вышло.** Ветка `if confirmation is not None` писалась под
требование TRIP-18 («набор рейсов подтверждённой даты берётся из
подтверждения, а не из шаблона»). Это требование про **восстановление**

**Чем грозит.** Пользователь подтвердил день, ошибся с шаблоном, и исправить
это через интерфейс не может. Хуже — диалог `ConfirmTripsDialog` прямо
пишет: «День уже подтверждён — набор поездок будет заменён» (строки 205–206
`dialogs.py`), — то есть **обещает замену, которой не будет**.

**Как чинить.** Разделить сценарии: если идентификаторы переданы явно —
использовать их и пересобрать поездки; если нет — восстанавливать из
подтверждения, как сейчас.

который не находится обычным поиском импортов.

Отдельно отмечу: я сначала заподозрил, что этот дефект влияет на работу
приложения, но проверка показала, что метод мёртвый. Сейчас он безвреден —
опасность появится, когда его кто-нибудь вызовет.

**Как чинить.** Либо удалить метод, либо перевести на `clock.today()`.
Оставлять «мёртвый + недетерминированный» — худший из вариантов.

### ⚪ Дефект 21. `DayResolver` кэширует контекст — не дефект, но требует аккуратности

**Где:** `student_planner/core/day_resolution.py:73`

**Сначала главное: это НЕ баг.** Я поставил пункт в список, чтобы показать
результат проверки — и объяснить, почему я его всё-таки не вычеркнул.

**Что происходит.** `DayResolver` при первом обращении читает якоря, предметы
и профили звонков в `_context_cache` и держит их до конца жизни объекта.
Замерено:

```
week_type(20.10.2026) до добавления якоря       = lower
-- добавляем якорь на 19.10.2026 (верхняя неделя) --
week_type(20.10.2026) тот же объект             = lower   <-- устарело
week_type(20.10.2026) новый DayResolver         = upper   <-- верно
```

**Почему это не дефект.** Во-первых, поведение явно задокументировано в
докстринге класса:

> «Один экземпляр кэширует якоря, предметы и задания; для перерисовки недели
> вызывающий создаёт новый экземпляр (данные меняются во время работы).»

Во-вторых, я проверил все семь мест создания в интерфейсе — **везде
создаётся новый экземпляр на каждую операцию**:

```
grid_editor.py:116     DayResolver(db).week_type(day)
main_window.py:186     DayResolver(self.db).week_type(...)
main_window.py:234     resolver = DayResolver(self.db)
schedule.py:344        resolver = DayResolver(self.db)
schedule.py:482        DayResolver(self.db).resolve(day)
schedule.py:527        DayResolver(self.db).resolve(day)
schedule.py:539        DayResolver(self.db).resolve(day)
```

Так что в текущем коде проблема не проявляется.

**Почему я его оставил.** Кэш без инвалидации — мина замедленного действия.
Достаточно, чтобы кто-то однажды сохранил resolver в `self.resolver` ради
«оптимизации», и расписание начнёт показывать старую неделю после смены
якоря. Ошибка будет плавающей и трудной для поиска.

**Что делать.** Либо ничего (поведение задокументировано и соблюдается), либо
добавить `invalidate()` — дёшево и снимает риск. Второй вариант я бы
рекомендовал, но это вопрос вкуса, а не исправления бага.
