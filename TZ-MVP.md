## 1. Общие сведения

### 1.1. Название

**Студенческий органайзер** / **Student Planner**.

### 1.2. Назначение и задачи

Приложение для персонального использования студентом колледжа. Распространяется с готовым стартовым набором (Прил. А), полностью редактируемым пользователем.

Ниже — перечень задач верхнего уровня. Это **сводка**: полные формулировки требований находятся в профильных разделах по ссылкам на ID, здесь они не дублируются.

1. `[О]` SCH-01 — расписание занятий с двухнедельным циклом (с запасом на N-недельный).
2. `[О]` BELL-01 — индивидуальная сетка звонков для каждого дня недели, с действием по диапазону дат.
3. `[О]` BELL-02 — двухчастные пары и цельные блоки.
4. `[О]` GRID-01 — редактирование всей недельной сетки занятий на одном экране.
5. `[О]` OVR-01 — разовые изменения расписания на дату.
6. `[О]` CAL-01 — учебные периоды: каникулы и праздники (период отменяет занятия на диапазоне дат).
7. `[О]` CAL-04 — ручное создание, редактирование и удаление учебных периодов.
8. `[О]` SUBJ-04 — справочник предметов: просмотр, добавление, редактирование, отключение используемого предмета (SUBJ-01…SUBJ-05, §8).
9. `[О]` RT-01 — шаблоны поездок: на каком транспорте студент добирается.
10. `[О]` TRIP-01 — подтверждение поездок дня и учёт фактических рейсов.
11. `[О]` FARE-01 — учёт транспортных расходов по тарифам, действующим на дату поездки.
12. `[О]` FARE-02 — расчёт экономии по льготам с откатом при истечении льготы.
13. `[О]` WAL-01 — кошелёк карты «Стрелка»: пополнения и остаток.
14. `[О]` HW-01 — домашние задания: привязка к предмету, дедлайн, статусы.

### 1.3. Целевая платформа

- `[О]` GEN-01 — Windows 10 / Windows 11 (x64).
- `[О]` GEN-02 — десктопное приложение.
- `[О]` GEN-03 — **работа** полностью офлайн: ни один сценарий не требует интернета.
- `[О]` GEN-04 — **установка** может требовать интернет однократно; допускается поставка с локальным wheelhouse.
- `[О]` GEN-05 — приложение не обращается к внешним справочникам (расписания транспорта, производственный календарь): все данные вводит пользователь (§34 `[У-5]`).

### 1.4. Хранение данных

- `[О]` DATA-01 — SQLite, файл локальный.
- `[О]` DATA-02 — путь по умолчанию `%APPDATA%\StudentPlanner\student_planner.db`.
- `[О]` DATA-03 — каталог создаётся автоматически при первом запуске.
- `[О]` DATA-04 — `journal_mode = DELETE` (файл пригоден для ручного копирования).
- `[О]` DATA-08 — все изменения данных в транзакциях.
- `[О]` DATA-19 — версия схемы фиксируется ключом `schema_version` (MVP: 1). При открытии БД с версией, отличной от известной приложению (выше **или** ниже), приложение отказывается стартовать, сообщает причину и **не изменяет файл**. Механизм миграции — v1.1.

### 1.5. Пользователь

- `[О]` GEN-06 — один пользователь, без авторизации. Он же «администратор» в смысле внесения глобальных правок (TODO-17): отдельных ролей нет.
- `[О]` GEN-07 — данные стартового набора не константы: любое значение редактируется, удаляется или добавляется пользователем без участия разработчика.

### 1.6. Язык

### 1.7. Валюта и время

- `[О]` GEN-09 — рубль, 2 знака, тип `Decimal`.
- `[О]` GEN-10 — время `ЧЧ:ММ`, 24 часа.
- `[О]` GEN-11 — дата в БД `ГГГГ-ММ-ДД`, в интерфейсе `ДД.ММ.ГГГГ`.

### 1.8. Нефункциональные требования

- `[О]` NFR-01 — минимальный экран 1366×768; **минимальный размер окна приложения — 1080×680** (`MainWindow.setMinimumSize`). Три колонки заданы горизонтальным `QSplitter` с регулируемыми границами: левая панель 250…560 px, правая 210…560 px, центральная зона не уже 360 px. При сужении окна колонки сжимаются до своих минимумов, а содержимое центральной зоны при нехватке места получает полосу прокрутки. Автоматического сворачивания правой панели и перехода колонок во вкладки в MVP **нет** — вместо этого пользователь сам освобождает место, утягивая разделитель (например, сузив левую панель до 250 px). 
- `[О]` NFR-02 — холодный запуск ≤ 3 с.
- `[О]` NFR-03 — любой отчёт при объёме ≤ 5000 поездок в БД строится ≤ 1 с.
- `[О]` NFR-04 — **второй экземпляр не блокируется.** MVP не использует named mutex и не отказывает в запуске: пользователь может открыть два окна на одном файле БД. Безопасность обеспечивают транзакции SQLite (`journal_mode = DELETE`, DATA-04, DATA-08): одновременная запись из двух окон сериализуется на уровне файла, но **изменения второго окна не появляются в первом до его перерисовки** («Обновить» / повторное открытие страницы). Ограничение осознанное: сценарий «два окна одновременно» для одного пользователя не типовой; фактическая проверка — `ACC-U-05` (ручная, проверяет, что данные не теряются, а не что второе окно не открывается).
- `[О]` NFR-05 — ни один сценарий не завершается необработанным исключением; лог в `%APPDATA%\StudentPlanner\logs\`.
- `[О]` NFR-06 — отсутствие сетевых вызовов во время работы.
- `[О]` NFR-07 — изменение любого значения стартового набора не требует перезапуска приложения.
- `[О]` NFR-09 — редактор недельной сетки: открытие ≤ 1 с, сохранение одной ячейки ≤ 300 мс при 30 слотах на две недели.
- `[О]` NFR-10 — каскадный пересчёт (CALC-04) при 5000 поездках в БД ≤ 1 с, в одной транзакции, с итоговым сообщением пользователю. **Скользящие периоды делают пересчёт обязательным, а не оптимальным.**
- `[О]` NFR-08 — в MVP не требуется ничего из перечисленного в §34.1.
- `[О]` NFR-11 — минимальные параметры машины: 64-разрядные Windows 10 / 11, 4 ГБ ОЗУ, 500 МБ свободного места на диске (из них ≤ 50 МБ — приложение с зависимостями, остальное — запас под БД и логи), экран не менее 1366×768 (NFR-01), клавиатура и указатель, русская локаль. Дискретных графических ускорителей и звуковых устройств требование не выдвигает.
- `[О]` NFR-12 — объём хранилища оценивается формулой, а не константой: размер файла БД линейен числу поездок (ориентир — эталонная фикстура NFR-03/NFR-10 на 5000 поездок ≤ 2 МБ), логи ограничены ротацией 10 МБ. Проверка — фактический замер на эталонной фикстуре (Прил. В, `ACC-M-101`).

### 1.9. Совместимость

- `[О]` GEN-15 — `requirements.txt` содержит **точные** версии всех прямых зависимостей (`==`, не диапазоны); приложение гарантированно работает только на зафиксированных версиях; установка из локального каталога пакетов (wheelhouse) возможна без интернета (GEN-04).
- `[О]` GEN-16 — файл БД переносим: копирование `student_planner.db` на другую машину с равной `schema_version` (DATA-19) открывает данные без конвертации. Отсюда ограничение на путевые значения: приложение **само** не записывает в БД развёрнутые абсолютные пути — значения по умолчанию вида `%APPDATA%\StudentPlanner\…` хранятся шаблоном, а не результатом раскрытия (`C:\Users\<имя>\…` был бы идентификатором пользователя, §30). Путь, введённый пользователем вручную (DATA-06, `backup_dir`), сохраняется как введён. После переноса отсутствующий каталог не является ошибкой запуска: приложение сообщает о проблеме и предлагает указать новый путь в UI (см. §37.2 «Каталог недоступен»).
- `[О]` GEN-17 — собираемый `exe` **не подписан** цифровой подписью; документация (DOC-02) обязана предупредить о возможном отображении Windows SmartScreen и антивирусных ложных срабатываниях и описать обход. Требование существует, чтобы неожиданное поведение при запуске не считалось дефектом приложения.

### 1.10. Актуальность и цель

Сведения, из которых состоит день студента колледжа, разложены по трём несвязанным источникам: расписание — в дневнике, на стенде или сайте колледжа; состояние карты «Стрелка» и номер поездки в текущем периоде — в приложении «Стрелка» или в памяти; расходы на проезд — в чеках и собственном счёте. Ни один источник не отвечает на два бытовых вопроса: **во сколько обойдётся сегодняшняя дорога** и **сколько занятий сегодня реально будет**. Отсюда три следствия, которые устраняет приложение:

1. Стоимость поездки известна только постфактум: номер поездки в скользящем 30-дневном периоде и порог скидки (35-я поездка) держатся в голове и «всплывают» при списании, часто в момент, когда выбрать способ оплаты уже нельзя.
2. Любое разовое изменение расписания (отмена пары, каникулы, практика, сессия) ломает весь маршрут дня: приходится вручную пересчитывать, какие поездки ещё нужны и что они будут стоить.
3. Учёт пополнений и расхода карты ведётся в трёх местах одновременно, поэтому остаток на «Стрелке» неизвестен ни до, ни после поездки.

**Цель** — свести расписание дня, поездки до колледжа и обратно и транспортные расходы в один локальный источник правды: офлайн (GEN-03), без участия разработчика при изменении любых данных (GEN-07), с автоматическим расчётом скользящего периода «Стрелки» (ALG-02) и экономии по льготе (FARE-10).

- `[О]` DOC-08 — формулировки настоящего подраздела используются в качестве Введения и п. 1 («Назначение разработки») пояснительной записки по присланному оглавлению КП (§37.6); в ТЗ они существуют как трассируемый источник, а не как риторика.

```
start.bat    — запуск приложения
```

`StudentPlanner.exe` (PyInstaller, one-folder); БД из `%APPDATA%`. Собранный exe обязателен, поскольку сам факт сборки проверяется приёмкой (`GEN-17`); требование `GEN-13`, описывавшее exe как *желательный* вариант, в MVP не входит.

### 2.3. Состав поставки `[О]` DOC-01

Код; `README.md` (§37.5); `requirements.txt`; `install.bat`; `start.bat`; `StudentPlanner.exe` (сборка PyInstaller, GEN-17); механизм инициализации (§2.5); `tests/` (Прил. В).

### 2.4. Стек `[О]` GEN-14

Python 3.13 (проверено на CPython 3.13.7; install.bat требует не ниже 3.11), PySide6 6.9.1 (Qt 6), SQLite через **стандартный модуль `sqlite3`** (ORM не используется), PyInstaller. Версии зависимостей зафиксированы точно (`==`) в `requirements.txt`. Иной стек допустим при выполнении NFR-01…NFR-10 и §32.

### 2.5. Первый запуск `[О]` FIRST-01…FIRST-16

- `[О]` FIRST-01 — при первом запуске создаётся БД и загружается **стартовый набор** (Прил. А): сетки звонков, предметы, шаблоны недель, шаблоны поездок, тарифы, настройки, якорь недели.
- `[О]` FIRST-15 — **первый шаг последовательности первого запуска** (перед FIRST-06): два поля — имя студента и группа (`student_name`, `group_title`). Отказ допустим: оба значения остаются пустой строкой (§30), а профиль (UI-04) показывает «Не указано» вместо пустоты. Требование существует потому, что оба ключа помечены `[О]` в реестре §30 и Прил. А.0 ожидает их заполненными, а спрашивать их было негде: отдельный мастер первоначальной настройки (`FIRST-07`) в MVP не обязателен. Ограничение UI-14 (≤ 3 поля) шаг не нарушает: полей ровно два, Enter сохраняет.
- `[О]` FIRST-16 — **ввод расписания при первом запуске.** После загрузки стартового набора (FIRST-01) приложение открывает редактор недельной сетки (§9.2) на текущем профиле и типе недели и предлагает ввести расписание своей группы; ввод заканчивается кнопкой «Готово». **Отказ реализован кнопкой «По умолчанию»**: она не изменяет ни одной строки стартового набора, закрывает экран и открывает главный (FIRST-03). Оба пути допустимы и не считаются ошибочными; выбор не запоминается как настройка, а повторный запуск шаг не повторяет (FIRST-04). Отказ обратим через GRID-11 («Вернуть стартовый набор недели») и FIRST-11. Шаг расположен **после** FIRST-15 и **до** FIRST-06, чтобы отказ от ввода расписания не блокировал остальные вопросы первого запуска.
- `[О]` FIRST-02 — все записи стартового набора доступны для редактирования и удаления сразу после первого запуска.
- `[О]` FIRST-03 — приложение открывает главный экран с расписанием на текущую дату и подставленными шаблонами поездок.
- `[О]` FIRST-04 — повторный запуск идемпотентен: существующие данные не перезаписываются.
- `[О]` FIRST-05 — в настройках доступна кнопка «Восстановить стартовый набор»: добавляет только отсутствующие записи Прил. А, не трогает изменённые.
- `[О]` FIRST-06 — при первом запуске приложение предлагает ввести начальное пополнение «Стрелки» (фактический остаток на карте, WAL-09); отказ допустим, предупреждение об остатке при этом не показывается.
- `[О]` FIRST-14 — при первом запуске приложение предлагает (с правом отказа) указать, сколько поездок уже засчитано на карте в текущем расчётном периоде и когда этот период начался (FARE-12). При отказе принимаются значения по умолчанию (`0` и «с первой поездки»), и счётчик приложения считается приближённым до конца текущего периода.
- `[О]` FIRST-11 — расписание другой группы вводится через редактор недельной сетки (§9.2): пользователь открывает редактор, выбирает тип недели и заполняет ячейки по одной (групповых операций в MVP нет, GRID-04); участие разработчика не требуется. Кнопка GRID-11 возвращает стартовый набор выбранной недели.
- `[О]` FIRST-12 — «Сбросить данные» (§29 SET-07) очищает **пользовательские** данные: домашние задания, поездки, подтверждения дня, пополнения «Стрелки», оверрайды расписания и учебные периоды. Справочники и стартовый набор (предметы, профили звонков и слоты, оба шаблона недели, тарифы, шаблоны поездок, якорь, настройки) при этом **не удаляются и не перезагружаются** — они остаются в БД как есть, поэтому повторной загрузки набора не требуется. Подтверждение — вводом слова «УДАЛИТЬ».

## 3. Термины

| Термин | Определение |
|---|---|
| **Учебный цикл** | Чередование недель; в MVP длина цикла 2 (верхняя/нижняя), длина хранится в якоре (`cycle_length`) |
| **Верхняя / нижняя неделя** | Половины двухнедельного цикла; неделя — понедельник–воскресенье |
| **Якорь недели** | Пара `(дата действия, опорная дата, тип опорной недели, длина цикла)`, по которой считается тип любой даты; новые якоря меняют только будущее |
| **Профиль звонков** | Набор блоков на день недели с диапазоном действия по датам. Поле `variant` (`default`, `friday_class_hour`, `custom`) в MVP всегда `default`; альтернативная пятница — v1.1 |
| **Позиция блока в сетке** (`slot_no`) | Порядковый номер блока в профиле; стабильный ключ шаблонов и оверрайдов |
| **Номер пары** (`pair_no`) | Академический номер для отображения; может не совпадать с `slot_no` |
| **Цельный блок** | Пара без внутренней перемены |
| **Двухчастный блок** | Пара из двух половин с внутренней переменой |
| **Подгруппа** (`group_mark`) | Сущность v1.1: метка занятия (`NULL` — общее, `1`, `2`). В MVP столбец остаётся в схеме резервом, приложение всегда пишет `NULL`; это задел v1.1 (§34.1 п. 16) |
| **Шаблон расписания** | Занятие для `(профиль звонков, тип недели, позиция блока)` |
| **Редактор недельной сетки** | Экран правки шаблона: вся неделя Пн–Сб × слоты, правка **по одной ячейке** за действие (§9.2); групповые операции — v1.1 |
| **Глобальное изменение** | Правка шаблона недели через редактор сетки; влияет на все будущие даты этого типа недели |
| **Точечное изменение** | Оверрайд на одну дату; шаблон не трогает (§10) |
| **Сиротский оверрайд** | Оверрайд, чей слот или занятие удалены из шаблона; обрабатывается ALG-10 |
| **Оверрайд** | Разовое изменение расписания на дату; шаблон не меняет. В MVP три типа: отмена (`cancel`), замена (`replace`), добавление (`add`); перенос (`move`) — v1.1 |
| **Учебный период** | Диапазон дат с особым режимом. В MVP два вида: каникулы (`vacation`) и праздник (`holiday`), оба отменяют занятия (`no_classes = 1`). Практика (`practice_educational`, `practice_industrial`) и экзаменационная сессия (`exam_session`) — v1.1 |
| **Пометка дня** | Сущность v1.1: ручное изменение режима конкретного дня поверх периодов и шаблона; в MVP отсутствует, состав v1.1 — §34.1 п. 28 |
| **Разрешение дня** | Результат ALG-04: какие занятия показываются на дату |
| **Тариф** | Запись цены с диапазоном действия: вид (`train_base`, `train_student`, `bus_base`, `strelka_stage1`, `strelka_stage2`), цена, даты |
| **Льгота** | Совокупность тарифов `train_student`, `strelka_stage1/2`; имеет срок действия, по истечении поездка считается по базовому тарифу |
| **Расчётный период «Стрелки»** | **Скользящие** 30 дней, начинающиеся с даты первой засчитанной поездки периода; следующий период открывает первая поездка после истечения текущего. Границы зависят от истории и пересчитываются при её изменении (ALG-02) |
| **Засчитанная поездка** | Поездка с `payment_method = 'strelka'`; только она увеличивает номер в периоде |
| **Порог скидки** | `strelka_first_limit` (35): поездки 1…порога — первая ступень, свыше — вторая |
| **Рейс** | Одна оплачиваемая транспортная операция, указанная фактически. Один рейс = одна запись расхода |
| **Шаблон поездки** | Именованный набор рейсов на одно направление; время справочное |
| **Набор рейсов дня** | Рейсы, фактически использованные в день; может отличаться от шаблона |
| **Подтверждение дня** | Действие, создающее записи расходов по выбранным рейсам за дату |
| **Учебная дата** | Дата учебного дня, к которому относятся поездки |
| **Кошелёк «Стрелки»** | Начальное пополнение + Σ(пополнения − комиссии) − Σ(оплаченные по карте поездки) |
| **Карта «Стрелка»** | Транспортная карта с накопительной скидкой «Копилка» на наземный транспорт |
| **Экзамен** | Сущность v1.1: экзамен, зачёт или дифференцированный зачёт вне сетки звонков; в MVP отсутствует, состав v1.1 — §34.1 п. 28 |
| **Домашнее задание** | Запись «предмет + дата сдачи + описание» со статусом `active`/`done`; входит в MVP (§12). Привязано к предмету и дате, а не к паре, поэтому не зависит от оверрайдов (HW-10) |
| **Дедлайн ДЗ** | Дата сдачи без времени: задание актуально до конца этой даты включительно (HW-02) |

## 5. Учебный календарь

### 5.1. Цикл недель

- `[О]` WEEK-01 — неделя: понедельник–воскресенье.
- `[О]` WEEK-02 — тип недели определяется **действующим якорем** (ALG-01) с длиной `cycle_length`.
- `[О]` WEEK-03 — начальный якорь создаётся из Прил. А при первом запуске (`cycle_length = 2`).
- `[О]` WEEK-04 — просмотр типа недели для любой даты.
- `[О]` WEEK-05 — действующий якорь правится на вкладке «Настройки → Недели»: изменение опорной даты, типа недели и комментария обновляет **существующую** запись `week_anchors` (в том числе историческую). Новый якорь добавляется отдельным действием «Добавить якорь» с собственной датой действия. Это осознанное упрощение: в MVP у пользователя один профиль обучения, и «переписать историю» ему проще, чем заводить второй якорь.
- `[О]` WEEK-06 — смена якоря влияет только на даты `>= effective_from` нового.
- `[О]` WEEK-07 — бейдж «Верхняя» / «Нижняя» в мини-календаре и на странице расписания.
- `[О]` WEEK-08 — чередование недель задаётся **якорем на вкладке «Настройки → Недели»**: дата действия (`effective_from`), опорная дата, тип недели. Отдельной кнопки «Изменить чередование недель…» на странице расписания в MVP **нет**: она лишь показывала подсказку и ничего не открывала, поэтому удалена — якорь правится в настройках, а расписание недели — кнопкой «Редактировать сетку недели…» на той же вкладке (SET-03).
- `[О]` WEEK-09 — в MVP `cycle_length = 2`; значения > 2 схемой допустимы, отображение «верхняя/нижняя» при этом не определено (TODO-15).

### 5.2. Учебные периоды

- `[О]` CAL-01 — период: вид, название, даты, комментарий.
- `[О]` CAL-02 — виды в MVP: `vacation` (каникулы), `holiday` (праздник). Оба отменяют занятия (`no_classes = 1`). Виды `practice_educational`, `practice_industrial`, `exam_session` и признак «ярлык» (`no_classes = 0`) — v1.1 (CAL-05…CAL-08, CAL-13).
- `[О]` CAL-03 — периоды могут перекрываться; при равенстве конкретности выигрывает последний созданный (ALG-04).
- `[О]` CAL-04 — пользователь создаёт, редактирует и удаляет периоды вручную; предзаполненного списка праздников нет (§34 `[У-5]`).
- `[О]` CAL-09 — в период с `no_classes = 1` страница расписания показывает название периода и причину вместо сетки (SCH-13).

## 7. Сетка звонков

### 7.1. Общие требования

- `[О]` BELL-02 — пара состоит из двух частей (двухчастный блок) либо является цельным блоком; число частей задаётся профилем (BELL-15), время блока — от начала первой части до окончания последней (BELL-06).
- `[О]` BELL-01 — у каждого дня недели собственный профиль звонков.
- `[О]` BELL-03 — профиль имеет `effective_from` / `effective_to` (nullable = бессрочно). Альтернативная пятница (`variant = friday_class_hour`) — v1.1; в MVP всегда `default`.
- `[О]` BELL-18 — для дня и даты выбирается профиль, действующий на дату; при отсутствии — ближайший предыдущий.
- `[О]` BELL-04 — блок хранит `slot_no`, тип, отображаемое имя, `pair_no` (nullable), упорядоченные части.
- `[О]` BELL-05 — часть хранит тип (`lesson` / `break`) и время начала и окончания.
- `[О]` BELL-06 — время блока = начало первой части и окончание последней; отдельно не хранится.
- `[О]` BELL-09 — блок «классный час» может не иметь предмета (`subject_id IS NULL`).

### 7.2. Редактирование

- `[О]` BELL-11 — просмотр сетки по дням и диапазонам действия.
- `[О]` BELL-12 — изменение времени частей с автопересчётом времени блока и проверкой пересечений.
- `[О]` BELL-13 — добавление и удаление блока **в конце** профиля.
- `[О]` BELL-15 — изменение числа частей внутри блока.
- `[О]` BELL-16 — вставка и удаление блока в середине запрещены, если для слота есть записи шаблона или оверрайдов.
- `[О]` BELL-17 — валидация: начало < окончание, части и блоки не пересекаются.
- `[О]` BELL-19 — создание нового профиля на день недели с новым диапазоном действия (например, зимняя сетка с 01.01).
- `[О]` BELL-20 — удаление профиля, на который ссылаются шаблоны или оверрайды, блокируется с предложением деактивации.

## 8. Справочник предметов

- `[О]` SUBJ-01 — предмет: код, название, преподаватель, кабинет, цвет, признак активности.
- `[О]` SUBJ-02 — уникальность `(code, name)`: несколько предметов могут иметь одинаковый код.
- `[О]` SUBJ-03 — в интерфейсе всегда показываются название, преподаватель, кабинет.
- `[О]` SUBJ-04 — справочник предметов — **раздел «Настройки → Предметы»**: таблица со столбцами «Название», «Преподаватель», «Кабинет», «Код», «Активен» (SUBJ-03) и кнопками «Добавить», «Изменить», «Отключить»/«Включить», «Удалить». Просмотр, добавление и правка доступны всегда; удаление — только если предмет не используется в шаблоне, оверрайде или ДЗ. Если предмет используется, вместо ошибки предлагается **отключить** его: он остаётся в базе и в прошлых записях, но перестаёт предлагаться в списках выбора. Отключённые предметы показываются в таблице серым с «Активен: нет».
- `[О]` SUBJ-05 — новый предмет создаётся в справочнике «Настройки → Предметы». Создания предмета **прямо из ячейки сетки** в MVP нет: в ячейке предмет только выбирается из списка или набирается по названию уже существующего (GRID-02). Причина: отдельный мини-диалог внутри редактора дублировал бы справочник и усложнял быстрый ввод расписания; ядро (`GridService.create_subject_for_cell`) готово к v1.1.

Стартовый состав — Прил. А.2.

## 9. Базовое расписание (шаблоны)

### 9.1. Хранение и редактирование

- `[О]` TPL-01 — занятие хранится как `(profile_id, week_type, slot_no, effective_from) → subject_id`; на одну позицию на одну дату приходится не более одной строки.
- `[О]` TPL-06 — редактирование: изменение предмета в слоте, очистка, копирование шаблона недели.
- `[О]` TPL-07 — изменение профиля звонков не сдвигает занятия, пока не изменился `slot_no`.
- `[О]` **TPL-08 — правка сетки действует с выбранной даты.** В шапке редактора есть поле «Действует с» (по умолчанию — открытая дата). Сохранение ячейки создаёт новую версию позиции с этой даты; более поздние версии той же позиции отбрасываются как перекрытые, более ранние сохраняются нетронутыми. Поэтому правка перестаёт менять прошлые недели: неделя до выбранной даты показывает прежнее расписание. Очистка с даты ставит надгробие (`subject_id IS NULL`): занятия нет начиная с этой даты, но прошлые недели сохраняют пару. Без даты (`effective_from IS NULL` в вызове) поведение прежнее и служит для стартового набора: история позиции заменяется одной базовой строкой. Версии независимы по `week_type` и по `profile_id`: правка нижней недели не затрагивает верхнюю.

### 9.2. Редактор недельной сетки

- `[О]` GRID-01 — один экран, показывающий всю недельную сетку (**Пн–Сб × все слоты профиля**, включая пустые) для выбранного типа недели и профиля дня. Пустые слоты в редакторе видны и заполняются; в дне расписания они скрыты (SCH-03).
- `[О]` GRID-02 — в каждой ячейке — выпадающий список предметов с автодополнением по названию, преподавателю и коду; выбор сохраняет ячейку немедленно, без общего «Сохранить»; пустое значение очищает ячейку. Предмет можно не только выбрать из списка, но и **набрать его название вручную**: сохранение срабатывает по Enter и по уходу фокуса, регистр и лишние пробелы по краям не важны, название ищется и без преподавателя (в списке подпись склеена как «Имя — Преподаватель»). Текст, не совпавший ни с одним предметом, в базу не пишется — подпись ячейки восстанавливается, данные не меняются.
- `[О]` GRID-03 — переключатель внутри редактора: тип недели (верхняя / нижняя). Переключатели варианта дня и подгруппы отсутствуют в MVP (оба относятся к v1.1).
- `[О]` GRID-05 — редактор **не изменяет `slot_no`**: очистка ячейки удаляет только запись шаблона, слот и его время остаются. Добавление и удаление слотов — только §7.2 (BELL-13, BELL-16).
- `[О]` GRID-06 — после любой правки редактора оверрайды дат, сославшиеся на удалённое занятие, не удаляются автоматически: они становятся сиротскими и обрабатываются ALG-10.
- `[О]` GRID-07 — редактор показывает в ячейке название, преподавателя и кабинет; при отсутствии предмета — пустую ячейку, кнопка «Очистить» неактивна.
- `[О]` GRID-08 — производительность — NFR-09.
- `[О]` GRID-11 — **«Вернуть стартовый набор недели»**: восстанавливает строки `schedule_templates` выбранного типа недели из Прил. А.3, не затрагивая оверрайды, профили звонков и расписание другого типа недели. Кнопка существует, чтобы отказ от ввода расписания при первом запуске (FIRST-16) был обратимым; перед восстановлением — подтверждение. Число перезаписываемых строк в тексте подтверждения не показывается — оно пишется в журнал.

Стартовые шаблоны — Прил. А.3.

## 10. Разовые изменения расписания

### 10.1. Двухуровневая модель

- `[О]` OVR-11 — глобальные изменения (начало семестра, другая группа, замена предмета во всех неделях) вносятся **только** через редактор недельной сетки (§9.2); точечные (болезнь преподавателя, отмена или замена одной пары) — **только** через оверрайды (§10.2).
- `[О]` OVR-12 — оверрайды переживают правку шаблона: изменение или очистка ячейки сетки не удаляет оверрайды дат; несоответствия обрабатываются ALG-10.

### 10.2. Оверрайды

- `[О]` OVR-01 — оверрайд изменяет расписание даты, не затрагивая шаблон.
- `[О]` OVR-02 — типы: `cancel`, `replace`, `add`. Тип `move` (перенос пары) в MVP отсутствует: `OVR-06` — v1.1 (§34.1 п. 32).
- `[О]` OVR-03 — ключ `(date, profile_id, slot_no)`, `part_seq` (nullable) зарезервирован.
- `[О]` OVR-04 — отмена: блок помечается отменённым, остальные **не смещаются**, шаблон не меняется. Отменённая карточка по умолчанию не показывается в дне (SCH-18). Особый случай: если занятие в блоке существует **только** благодаря оверрайду `add` (в шаблоне слота нет), отмена удаляет все оверрайды этого блока целиком — иначе `add` остался бы в силе, занятие продолжало бы показываться, а повторная отмена упиралась бы в OVR-08. Пользователь видит результат: занятие исчезает.
- `[О]` OVR-05 — замена: предмет, преподаватель, кабинет, комментарий; время по умолчанию сохраняется, может быть задано своё. Замена доступна и на отменённой паре: это путь «убрал одну — поставил другую», прежний `cancel` того же блока при этом снимается. **Диалог открывается на текущем предмете пары** и подставляет преподавателя и кабинет из справочника предметов при каждом выборе; поля остаются редактируемыми для разовых отличий (другой преподаватель, другая аудитория). Пустое поле означает «как в справочнике», а не «нет данных».
- `[О]` OVR-07 — добавление: в свободный слот или на пользовательское время. **Блок выбирается в диалоге явно** — списком всех блоков дня с пометкой «свободен»/«занят — заменить»; по умолчанию подставлен первый свободный. Отменённый блок считается свободным: пара в этот день не показывается (SCH-18), поэтому на место отменённой можно поставить новую. Автоматический выбор «только первый свободный» не давал поставить занятие первой парой — оно всегда уезжало в конец дня. Преподаватель и кабинет подставляются из справочника выбранного предмета и остаются редактируемыми.
- `[О]` OVR-08 — конфликты: не более одного оверрайда из `cancel`/`replace` на `(date, profile_id, slot_no)`; `add` в занятый слот запрещён; **второй `add` в тот же слот запрещён** (добавленное занятие правят, а не добавляют повторно); «последний победил» не применяется. Исключения: `replace` поверх `cancel` того же блока **разрешён** (OVR-05); `add` в блок с `cancel` **разрешён** и превращается в `replace`, если в блоке есть занятие по шаблону, — иначе `add` на слот с шаблоном не отображался бы (ALG-04). Правила для `move`, включая запрет переноса в занятый слот, — v1.1 вместе с OVR-06.
- `[О]` OVR-09 — изменение применяется к блоку целиком; `part_seq` для v1.2.
- `[О]` OVR-10 — внутри периода с `no_classes = 1` оверрайды не применяются: период отменяет занятия целиком (`[У-20]`). Возможность вернуть отдельному дню занятия (`force_class`) появится в v1.1 вместе с пометками дня.
- `[О]` **OVR-11 — удаление изменения пары.** На карточке занятия, у которого есть изменение этой даты, показывается кнопка «↺ Убрать изменение» (предупреждающий стиль). Действие удаляет оверрайд: снятая отмена возвращает пару в расписание, снятая замена возвращает предмет из шаблона недели. Сетка недели не меняется — её правит только редактор сетки (TPL-08). Дефект: отменённую и заменённую пару нельзя было ни удалить, ни заменить повторно — повторная замена упиралась в «уже есть изменение `replace`» (OVR-08), и изменение оставалось навсегда.
- `[О]` **UI-25 — набор кнопок карточки зависит от состояния пары.** Кнопки не накапливаются: показываются только осмысленные действия. Пара по плану — «Отменить», «Заменить». Отменённая — «Заменить» и «↺ Убрать изменение»: замену предлагаем как путь «убрал одну — поставил другую», а «Отменить» уже нажата и ничего не делает. Заменённая — только «↺ Убрать изменение»: замену снимают ею, а отменять заменённую пару нечего. Пара, добавленная оверрайдом `add`, — как по плану; её изменение снимает «Отменить» (OVR-04), отдельного «Убрать» у неё нет. Дефект: «Заменить» и «Убрать изменение» висели одновременно, и блок пары вырастал с 62 до 86 px, сдвигая день.

## 11. Отображение расписания

- `[О]` SCH-01 — расписание занятий строится на двухнедельном цикле (с запасом на N-недельный): тип недели определяет действующий якорь (WEEK-02, ALG-01), данные берутся из шаблона и оверрайдов дат.
- `[О]` SCH-02 — **три режима**: текущая неделя, следующая неделя, выбранная дата. Режимы «шаблон верхней недели» и «шаблон нижней недели» отсутствуют (`[У-22]`): шаблон просматривают и правят в редакторе сетки (§9.2, GRID-01), а расписание всегда показывает конкретные даты. Подпись режима выбранной даты содержит дату и тип недели, чтобы не путать его с «текущей неделей».
- `[О]` SCH-03 — недельная сетка: колонки Пн–Сб; строки — блоки профиля дня. **Слоты без занятия и без оверрайда в дне не показываются** (в отличие от редактора сетки, GRID-01). День, в котором все слоты пусты, отображается как «Занятий нет» (SCH-07).
- `[О]` SCH-16 — воскресенье в сетку не входит; период с особым ярлыком на воскресенье показывается отдельной строкой «Воскресенье» под сеткой только при непустом содержании. События уровня «экзамен» и «пометка дня» на воскресенье появятся в v1.1 и займут ту же строку.
- `[О]` SCH-04 — карточка занятия: время, предмет, преподаватель, кабинет, статус, номер пары, бейдж домашнего задания (HW-06).
- `[О]` SCH-05 — статусы: «По плану», «Отменено», «Заменено», «Добавлено». Статус «Перенесено» в MVP не выставляется, поскольку перенос (OVR-06) — v1.1, и в перечислении `LessonStatus` его **нет**; при возврате переноса значение будет добавлено вместе с миграцией схемы.
- `[О]` SCH-06 — переключатель свёрнутого и развёрнутого вида двухчастных блоков.
- `[О]` SCH-13 — день внутри периода с `no_classes = 1` показывает название периода и причину вместо сетки.
- `[О]` SCH-07 — пустое состояние дня: «Занятий нет» и одно действие «Редактировать сетку недели». `EmptyState` поддерживает одно действие, поэтому отдельной кнопки «Добавить занятие» в пустом состоянии нет: добавить занятие можно в редакторе сетки (GRID-01) или кнопкой «Добавить занятие» на самой странице дня.
- `[О]` SCH-08 — сброс изменений даты: оверрайды выбранной даты удаляются, расписание возвращается к шаблонной сетке. В MVP отдельной кнопки «Сбросить изменения на эту дату» **нет**; удаление выполняется по одному — действием «Удалить изменение» в предупреждении о сиротских оверрайдах (SCH-19) либо сменой шаблона дня в подтверждении поездок. Массового сброса всех оверрайдов даты одной кнопкой в MVP не предусмотрено.
- `[О]` SCH-17 — сиротский оверрайд отображается в карточке дня предупреждением и не применяется к расписанию (ALG-10). Внутри периода с `no_classes = 1` карточка показывает только период (SCH-13), поэтому предупреждений о сиротах в такие дни не выводится: оверрайды там не применяются вовсе (OVR-10).

## 12. Домашние задания `[О]`

- `[О]` HW-01 — сущность: предмет, дата сдачи, описание, статус, даты создания и выполнения. Поле `group_mark` — резерв v1.1: приложение его **не заполняет, всегда пишет `NULL`** и по нему не фильтрует. Ограничение схемы при этом допускает значения 1 и 2 (как и в `schedule_templates`, `schedule_overrides`), поэтому ручная запись `group_mark = 1` не отклоняется — это задел под v1.1, а не действующая возможность.
- `[О]` HW-02 — дата сдачи без времени; задание актуально до конца указанной даты включительно.
- `[О]` HW-03 — статусы `active`, `done`; иных значений нет.
- `[О]` HW-04 — создание, редактирование, удаление, отметка выполнения и фильтры: «Все», «Активные», «Выполненные», «Просроченные», а также фильтр по предмету. Порядок пунктов фильтра статуса — именно такой, «Все» стоит первым.
- `[О]` HW-05 — виджет заданий в правой панели: **текущая и следующая календарные недели** — от сегодняшнего дня до воскресенья следующей недели включительно. Показываются только активные задания; просроченные в виджет не попадают (они видны на странице заданий отдельной группой). Внутри виджета список не обрезается: он выводится в прокручиваемой области ограниченной высоты, поэтому видны все задания окна, а панель не выдавливает остальные карточки. Есть кнопка «Все задания», ведущая на страницу заданий. Пустой список отображается состоянием «Заданий нет». Перехода к конкретному заданию из виджета в MVP нет.
- `[О]` HW-06 — бейдж на карточке занятия (SCH-04): задание показывается на паре того же предмета в день сдачи. Правило сопоставления — по `subject_id` и дате; при нескольких заданиях — счётчик. Считаются только **активные** задания: выполненные бейдж не показывают, даже если дата сдачи совпадает.
- `[О]` HW-07 — **быстрый ввод** (§20 UI-14) обязателен: данные поступают со слов преподавателя на ходу, поэтому создание задания укладывается в лимит «≤ 3 поля до сохранения, Enter сохраняет».
- `[О]` HW-08 — просроченным считается активное задание с датой сдачи раньше сегодняшней; просрочка **не меняет** статус автоматически и хранится вычисляемой. Отдельного поля «просрочено» в схеме нет.
- `[О]` HW-09 — удаление предмета, на который ссылаются задания, запрещено; используется отключение предмета (SUBJ-03, SUBJ-04), и задания остаются доступными на чтение.
- `[О]` HW-10 — задания хранятся независимо от расписания: отмена или замена пары не удаляет и не переносит задание, поскольку дедлайн задан датой, а не парой.

## 15. Подтверждение поездок дня

- `[О]` TRIP-01 — для выбранной даты два блока: «Туда» и «Обратно».
- `[О]` TRIP-02 — выбор шаблона направления из списка активных шаблонов. Сборка произвольного набора рейсов в окне подтверждения в MVP **отсутствует**: рейсы дня задаются выбранным шаблоном, а лишняя поездка вносится ручной записью в журнале (REP-14, `[У-16]`).
- `[О]` TRIP-03 — **автоподстановка по последнему использованному** для этого дня недели и направления; при отсутствии истории — первый активный шаблон.
- `[О]` TRIP-04 — правка набора рейсов на дату без изменения шаблона: смена выбранного шаблона в блоке «Туда» или «Обратно» пересобирает поездки даты заново, шаблон при этом не меняется (RT-13 правит шаблон отдельно, в разделе «Шаблоны»).
- `[О]` TRIP-05 — «Сохранить как шаблон» создаёт новый шаблон из текущего набора.
- `[О]` TRIP-06 — направление снимается галочкой; снятое не создаёт поездок.
- `[О]` TRIP-07 — окно подтверждения показывает: дату, оба направления с выбранными шаблонами, число рейсов (туда / обратно / всего), предварительную стоимость и экономию, признак того, что день уже подтверждён (повторное подтверждение перезапишет автоматические поездки, TRIP-09). Прогноз номера поездки «до и после», границы периода после подтверждения и остаток кошелька после подтверждения в окне подтверждения **не показываются** — эти же сведения даёт кнопка «Проверить стоимость» на вкладке подтверждения (TRIP-14), где расчёт выполняется тем же ALG-02/ALG-09.
- `[О]` TRIP-08 — каждый рейс создаёт отдельную запись расхода; два автобуса → две поездки, счётчик +2.
- `[О]` TRIP-09 — идемпотентность подтверждения дня (`UNIQUE(study_date)` в `trip_confirmations`); повторное подтверждение **не создаёт дубли и не удаляет ручные поездки даты** (REP-14).
- `[О]` TRIP-10 — удаление подтверждения: автоматические поездки удаляются, ручные (`is_manual = 1`) сохраняются.
- `[О]` TRIP-11 — дата любая; для прошлых — предупреждение.
- `[О]` TRIP-18 — набор рейсов дня восстанавливается **из подтверждения даты**: `trip_confirmations` хранит `outbound_template_id` и `return_template_id`, и при повторном открытии даты приложение подставляет именно эти шаблоны. Поездки (`transport_rides`) — производные записи и для восстановления набора не читаются.
- `[О]` TRIP-19 — если хотя бы один рейс даты не имеет действующего на `ride_date` базового тарифа (ALG-09), подтверждение блокируется с предложением задать тариф.

## 17. Тарифы, «Стрелка» и кошелёк

### 17.1. Тарифы

- `[О]` FARE-01 — тариф — запись `(kind, price, effective_from, effective_to, is_active)`; виды: `train_base`, `train_student`, `bus_base`, `strelka_stage1`, `strelka_stage2`.
- `[О]` FARE-02 — на одну дату и один `kind` не более одного действующего тарифа; пересечение диапазонов одного вида — ошибка сохранения. В MVP, где `vehicle` всегда NULL (`[У-17]`), условие вырождается в `(kind, дата)`; с v1.1 (FARE-14) — `(kind, vehicle, дата)`.
- `[О]` FARE-03 — электричка: `train_student`; при отсутствии льготы на `ride_date` — `train_base` (FARE-10, RT-17).
- `[О]` FARE-04 — автобус: базовый `bus_base`, **единый для всех маршрутов**: номер рейса на цену не влияет (`[У-17]`).
- `[О]` FARE-05 — способы оплаты автобуса: только `strelka` и `debit_card`; наличные отсутствуют.
- `[О]` FARE-06 — расчётный период «Стрелки» — **скользящие 30 дней** (`strelka_period_days`), начинающиеся с даты первой засчитанной поездки; следующий период открывает первая поездка после истечения текущего. Границы вычисляются по ALG-02 и **не образуют справочника**: отдельной таблицы нет, а начало периода, относящееся к поездке, хранится **снапшотом** `transport_rides.period_start_date` и обновляется каскадным пересчётом (CALC-04). Прежнее упрощение `[У-1]` (фиксированная дата) **отменено в v1.6**.
- `[О]` FARE-07 — **две ступени** скидки: поездки 1…`strelka_first_limit` — `strelka_stage1`; свыше — `strelka_stage2`. Порог `strelka_first_limit` — единственное значение без срока действия (`[У-9]`). Многоступенчатая лестница — v1.2 (TODO-9).
- `[О]` FARE-08 — дебетовая карта: полная стоимость `bus_base`, счётчик не увеличивает, экономии не даёт.
- `[О]` FARE-09 — формулы стоимости и экономии; `Decimal`, `ROUND_HALF_UP`; цены поездок — снапшот на момент подтверждения. Расчётная стоимость поездки не превышает базовую: если по формуле льготная цена оказалась бы выше `base`, применяется `base` (защита от ступени, заданной пользователем выше базового тарифа), экономия при этом равна 0.
- `[О]` FARE-10 — **откат льготы**: если на `ride_date` нет действующего льготного тарифа вида, поездка считается по соответствующему базовому (`train_student → train_base`, `strelka_stage* → bus_base`), экономия = 0; счётчик «Стрелки» при этом продолжает увеличиваться.
- `[О]` FARE-11 — экран «Тарифы» (в разделе настроек «Транспорт»): список тарифов по видам с датами действия и действие «Добавить тариф…». Правка и удаление тарифа из интерфейса MVP **недоступны**: список только читается и пополняется. Удаление тарифа, использованного поездками, блокируется на уровне данных (цены поездок — снапшоты). Чтобы изменить цену, добавляют новый тариф с более поздней `effective_from` — прошлые поездки сохраняют старую цену (ALG-09).
- `[О]` FARE-12 — **параметры начала учёта**: `strelka_period_anchor_date` (дата начала периода, идущего на карте на момент начала учёта; **пустая строка = «не задано»**, период начнётся с первой поездки) и `strelka_initial_ride_count` (число уже засчитанных поездок в этом периоде; `0` = учётся всё с нуля). Оба применяются **только к первому периоду** цепочки. Их изменение запускает полный каскадный пересчёт (CALC-04). Предложение ввести — FIRST-14.

### 17.2. Кошелёк «Стрелки»

- `[О]` WAL-01 — операция пополнения: дата, сумма, способ пополнения, комментарий.
- `[О]` WAL-03 — остаток = Σ(пополнения − комиссии) − Σ(оплаченные поездки `strelka`), ALG-07.
- `[О]` WAL-04 — **пополнение не является расходом**: в отчётах «пополнено», «потрачено», «остаток», «экономия» — четыре отдельные колонки, не суммируемые.
- `[О]` WAL-05 — предупреждение в интерфейсе, если остаток меньше `strelka_low_balance_warn` × стоимость следующей поездки по «Стрелке» (ALG-09 и ALG-02 на сегодня). **До первого пополнения предупреждение не показывается**, виджет отображает «Остаток не задан».
- `[О]` WAL-06 — предупреждение — жёлтый бейдж в виджете «Стрелка» и в окне подтверждения дня. Системные уведомления — v1.1.
- `[О]` WAL-07 — удаление и правка пополнения пересчитывают остаток немедленно.
- `[О]` WAL-08 — кошелёк только для «Стрелки»; дебетовая карта — способ оплаты без остатка (`[У-6]`).
- `[О]` WAL-09 — **первое пополнение = фактический остаток на карте** на дату начала учёта; вносится при первом запуске (FIRST-06) или позже из журнала пополнений с комментарием «начальный остаток».

## 18. Расчёт поездок при подтверждении

- `[О]` CALC-01 — несколько автобусных рейсов по «Стрелке» считаются последовательно в порядке следования.
- `[О]` CALC-02 — дебетовая карта счётчик не увеличивает и не «съедает» номер следующего рейса.
- `[О]` CALC-03 — номер поездки определяется по фактической дате и истории засчитанных поездок в её вычисленном периоде (ALG-02, ALG-03); при открытии нового периода счёт начинается с 1.
- `[О]` CALC-04 — **каскадный пересчёт**: при добавлении, правке, удалении поездки, смене способа оплаты и при изменении `FARE-12` пересчитываются **все** поездки в порядке `(ride_date, id)` — границы периодов, номера, стоимости (ALG-09) и остаток; в одной транзакции, пользователю показывается итог (сколько записей изменено и на какую сумму). Пересчитываются все поездки, а не только начиная с даты изменения: параметр «с даты» влияет лишь на формулировку сообщения. Пересчёт затрагивает и поездки по дебетовой карте и электричке — у них обновляются границы периода и номер, хотя стоимость от ступени «Стрелки» не зависит. Скользящие периоды делают этот пересчёт обязательным: вставка одной прошлой поездки меняет ступень последующих.
- `[О]` CALC-06 — пересчёт остатка кошелька выполняется вместе с пересчётом поездок.
- `[О]` CALC-07 — производительность пересчёта — NFR-10.

## 19. Расходы и аналитика

- `[О]` REP-01 — журнал поездок: дата поездки, учебная дата, тип недели (снапшот), направление, шаблон, транспорт, номер рейса, базовая стоимость, оплата, экономия, способ оплаты, **границы вычисленного периода (`period_start_date`)**, номер в периоде, признак «вручную», комментарий.
- `[О]` REP-02 — функции журнала: просмотр, добавление, правка, удаление, фильтры по дате, типу транспорта, способу оплаты.
- `[О]` REP-14 — **ручная поездка**: запись в журнале может быть создана на любую дату и направление независимо от подтверждения дня (окна, поездка домой среди дня, разовый маршрут); создаётся с `is_manual = 1`, участвует в счётчике и остатке наравне с остальными и **не удаляется** при удалении подтверждения дня (TRIP-10). Кнопка «Добавить поездку» доступна на журнале постоянно, не только в пустом состоянии; пустое состояние журнала содержит ту же кнопку.
- `[О]` REP-03 — отчётные периоды: день, неделя, месяц, а также «Всё время» (без ограничения периода). Полугодие, год и переключатель «по учебным дням» — v1.1. Группировка по `ride_date`.
- `[О]` REP-04 — показатели: потрачено; по электричке; по автобусам; по «Стрелке»; по дебетовой карте; экономия; количество поездок; по «Стрелке»; дебетовой картой; структура расходов.
- `[О]` REP-09 — показатели кошелька: пополнено за период, комиссии, остаток на конец периода — отдельный блок, не входящий в «потрачено» (WAL-04).
- `[О]` REP-05 — виджет «Стрелка»: **вычисленные границы текущего расчётного периода** (`period_start_date` … `+ 29 дней`), номер следующей поездки, стоимость следующей поездки, экономия за период, остаток. В состоянии ALG-02 шаг 1 (поездок ещё нет, якорь не задан) вместо границ выводится прочерк «—», а вместо номера и стоимости следующей поездки — текст «Поездок ещё не было»; отдельного бейджа «До начала учёта» в MVP нет. Пометка «с учётом N поездок до начала учёта» при `strelka_initial_ride_count > 0` выводится не в виджете, а подписью в «Настройки → Транспорт», рядом с полем счётчика. Флаг «счётчик приближённый» (`approximate`) вычисляется и используется в расчёте, но в интерфейсе MVP **не отображается** — о приближённости счётчика говорит только подпись о начальном счётчике.
- `[О]` REP-07 — пустое состояние отчёта: «Поездок за период нет» без кнопок; пустое состояние журнала содержит кнопку «Добавить поездку». Кнопка «Подтвердить поездки» находится на вкладке подтверждения дня, а не в журнале.
- `[О]` REP-08 — «Пересчитать счётчик «Стрелки»» с подтверждением запускает CALC-04 в полном объёме.

## 20. Интерфейс: общие требования

- `[О]` UI-01 — тёмная тема: тёмно-серый фон, панели светлее/темнее, насыщенный синий акцент, успех зелёный, предупреждение жёлтый, ошибка красный, отменено приглушённо-серое.

Отдельного индикатора для операций длиннее 300 мс в MVP **нет**: все операции укладываются в это время на целевой конфигурации (NFR-12), а индикатор выполнения в интерфейсе не выводится.
- `[О]` UI-14 — **быстрый ввод**: лимит «≤ 3 поля до сохранения, Enter сохраняет» в MVP действует для отмены пары, подтверждения поездок дня, пополнения «Стрелки» и **ручной поездки (REP-14)**. Прочие операции (редактор сетки, замена, перенос, добавление занятия, тариф, период) выполняются через компактный диалог или таблицу без жёсткого лимита, но с автодополнением. На домашние задания лимит распространяется в MVP (`HW-07`); на экзамены — с v1.1.

## 31. Алгоритмы

### ALG-01. Тип недели `[О]`

1. Найти якорь с максимальной `effective_from <= дата`.
2. Найти понедельник недели даты и понедельник `base_date`.
3. `n = (разница_недель mod cycle_length)`.
4. При `cycle_length = 2`: `n = 0` → тип совпадает с `base_type`, `n = 1` → противоположный.
5. При `cycle_length > 2` поведение в MVP не определено (TODO-15); схема значение допускает.

Смена якоря меняет только даты `>= effective_from` нового (WEEK-06).

### ALG-02. Расчётный период «Стрелки» (скользящий) `[О]`

Вход: дата `D`. Данные: `R` — множество засчитанных поездок (`payment_method = 'strelka'`), `anchor0` = `strelka_period_anchor_date`, `cnt0` = `strelka_initial_ride_count`, `LEN` = `strelka_period_days` (30).

**Обозначения.** `R` — **все** засчитанные поездки (`payment_method = 'strelka'`), включая состоявшиеся на дату `D`. Различение «до `D`» и «на `D`» делается не на входе, а на шагах 6 и 7: шаг 6 считает поездки строго раньше `D`, шаг 7 — порядковый номер среди поездок на `D`. Именно это разделение лечит офф-бай-у-он, при котором пересчитываемая поездка попадает в собственный счётчик дважды.

1. **Учёт не начат.** Если в `R` нет ни одной засчитанной поездки **и** `anchor0` не задана (пустая строка) → якорь не определён: `period_start_date = NULL`, но номер всё равно вычисляется (шаг 8 при `n_prev = 0`, `k = 1` даёт `cnt0 + 1`), ступень — первая. Штатное состояние сразу после первого запуска: поездок ещё нет, следующий номер уже известен, границы появятся с первой поездкой.
2. `anchor` = `anchor0`, если задана; иначе — дата самой ранней поездки в `R`.
3. **До начала учёта.** Если `D < anchor` → `period_start_date = NULL`, `ride_number_in_period = NULL`, ступень — первая, бейдж «До начала учёта». Шаги 1 и 3 **взаимоисключающи**: якорь не определён только в случае шага 1, поэтому сравнение `D < anchor` на шаге 3 всегда имеет смысл. В отличие от шага 1 здесь номера нет — поездка раньше начала учёта не относится к текущему периоду карты.
4. Цепочка границ строится по поездкам `R` (включая состоявшиеся на `D`):
   ```
   start = anchor
   пока D > start + LEN − 1:                       # D вне текущего периода
       next = дата самой ранней поездки в R с датой > start + LEN − 1
       если next существует и next <= D:
           start = next                            # период открыла первая поездка после истечения
       иначе:
           start = D                               # такой поездки нет (или она сама на D):
           остановиться                            # период открывает D
   period_start = start
   period_end   = start + LEN − 1
   ```
   Ветви «нет `next`», «`next > D`» и «`next == D`» дают один результат: `start = D`. Различать их при реализации не нужно.
5. `period_start` и `period_end` — границы расчётного периода для даты `D`.
6. `n_prev` = число засчитанных поездок с датой в `[period_start, D)` — **строго раньше** `D`.
7. `k` = порядковый номер пересчитываемой поездки среди поездок на дате `D` в порядке `id`; для новой, ещё не сохранённой поездки `k = 1`.
8. `номер` = `n_prev + k`, плюс `cnt0`, если `period_start == anchor` (первый, «догоняющий» период цепочки). В состоянии шага 1 оба не определены — условие считается **выполненным**, и номер равен `cnt0 + 1`. В остальных периодах цепочки `cnt0` не применяется.
9. Ступень: `номер <= strelka_first_limit` → `strelka_stage1`, иначе `strelka_stage2`.

**Следствия, важные для реализации:**

- Границы периодов — функция от всей истории `R`. Добавление, удаление или правка любой засчитанной поездки могут изменить границы и номера **всех последующих** поездок → обязательный CALC-04.
- Поездка после истечения текущего периода **открывает новый** период с номера 1 (ветвь `next <= D`; в примере — 12.10 и 15.11).
- Разрыв в поездках длиннее `LEN` дней отдельных правил не требует: он проходит той же ветвью и даёт новый период с номера 1.
- Шаги 6–7 разделяют «сколько поездок было до `D`» и «которая по счёту поездка на `D`». Без этого разделения пересчёт существующей поездки дважды засчитывает её саму (офф-бай-у-он в номере и, как следствие, в ступени).
- `cnt0` применяется только к первому периоду цепочки (шаг 8).
- **Устаревший якорь самокорректируется.** Если `anchor` задана намного раньше первой поездки так, что её окно `[anchor, anchor + LEN − 1]` уже истекло, шаг 4 на первой поездке получает `next == D` и открывает период её датой: ошибочная старая дата не искажает номера последующих поездок. Поэтому DATA-21 разрешает `anchor` раньше первой поездки — это штатный случай «период на карте начался до начала учёта», а не ошибка.

**Пример** (`anchor0` = «не задано», `cnt0 = 0`, `LEN = 30`, `strelka_first_limit = 35`). Фикстура А: в периоде 1 `[07.09, 06.10]` — 22 учебных дня по 2 засчитанные поездки (44 всего, график Пн–Пт); фикстура Б: те же 30 дней, 26 учебных дней по 2 поездки (52 всего, Пн–Сб). **На датах позже 06.10 поездки есть только в даты, названные в таблице** — разрывы 07.10–11.10, 11.11–14.11, 16.11–17.12 принадлежат обеим фикстурам.

| Дата события | Фикстура А (44 в периоде 1) | Фикстура Б (52 в периоде 1) |
|---|---|---|
| 07.09 — первая поездка | `anchor0` не задана → `anchor = 07.09`, период 1 = `[07.09, 06.10]`, `n_prev = 0`, `k = 1` → номер 1, ступень 1 | то же |
| Граница периода 1 (06.10) | `n_prev = 42`, `k = 1` → номер **43** > 35 → ступень 2; следующая поездка дня → 44 (итог периода 44) | `n_prev = 50`, `k = 1` → номер **51** → ступень 2; следующая → 52 (итог периода 52) |
| 12.10 — первая поездка после 06.10 | `next = 12.10 <= D` → период 2 = `[12.10, 10.11]`, `n_prev = 0`, номер 1 | то же |
| 15.11 — первая поездка после 10.11 (между 10.11 и 15.11 поездок не было) | `next = 15.11 <= D` → период 3 = `[15.11, 14.12]`, номер 1 | то же |
| 20.11 — запрос виджета «сколько будет стоить следующая поездка», **период 3 ещё действует** | `20.11 > 14.12` ложно → цикл не выполняется, границы остаются `[15.11, 14.12]`. Поездки: 2 на 15.11, 16–19.11 поездок не было → `n_prev = 2`, `k = 1` → номер **3**, ступень 1 | то же |
| 18.12 — тот же запрос, поездок после 14.12 не было | `18.12 > 14.12` → вход в цикл; `next` не существует ⇒ ветвь «нет `next`» ⇒ `start = D = 18.12`, период 4 = `[18.12, 16.01]`, `n_prev = 0`, `k = 1` → номер 1, ступень 1. **Границы предварительные:** если следующая поездка состоится позже 18.12, период откроется её датой и показанные границы устареют (REP-05) | то же |

**Альтернатива строке 15.11** (не продолжение таблицы): если бы первая поездка после истечения периода 2 (`[12.10, 10.11]`) состоялась не 15.11, а 16.11, то период 3 открылся бы датой 16.11: `[16.11, 15.12]`, номер 1. Границы задаёт первая поездка окна, а не календарь — сдвиг первой поездки сдвигает всю цепочку.

> **Оговорка к примеру (обязательна для чтения).** Даты иллюстративны: пример **не** утверждает, сколько учебных дней реально попадает в окно по календарю 2026, и не выводит из него `n_prev` — числа принадлежат фикстуре, как в TEST-01. Проверяется механика ALG-02: цепочка границ, переход порога и поведение запроса виджета. Поездка в выходный день (15.11) допустима: шаблон поездки привязан к направлению, а не к учебному дню (TRIP-03, REP-14).

### ALG-03. Номер поездки `[О]`

`номер` по ALG-02 шаг 8; точность обеспечивает каскадный пересчёт CALC-04. Засчитываются только `strelka` (DATA-14): `debit_card` и `train_student` не влияют (CALC-02, RT-17).

### ALG-04. Разрешение учебного дня `[О]`

Остановка на первом сработавшем шаге. В MVP четыре шага; с v1.1 перед ними встанут пометки дня (MARK-01…05), при этом пометка приоритетнее периода.

1. Период, содержащий дату, с `no_classes = 1` → **занятий нет**, отображается название (при пересечении — последний созданный период). В MVP единственные виды периода — `vacation` и `holiday`, оба с `no_classes = 1`.
2. Профиль звонков: вариант для дня недели, действующий на дату (BELL-18). В MVP вариант всегда `default`.
3. Шаблон расписания `(profile_id, тип недели по ALG-01, slot_no)`.
4. Оверрайды даты (OVR-08, ALG-10) → фактическое расписание. Слоты без занятия и без оверрайда в дне не отображаются (SCH-03). Внутри периода с `no_classes = 1` оверрайды не применяются (OVR-10, `[У-20]`).

### ALG-05. `T_start` / `T_end` `[О]`

Начало первого и окончание последнего неотменённого блока фактического расписания дня; только для отображения в виджете.

### ALG-06. Подтверждение поездок дня `[О]`

1. Выбор даты (виджет или календарь).
2. ALG-04 → фактическое расписание; ALG-05 → отображение; тип недели по ALG-01.
3. Подстановка шаблонов: последний использованный для этого дня недели и направления (TRIP-03) → при отсутствии истории первый активный. Переопределение маршрута периодом (TRIP-17) — v1.1.
4. Правка рейсов или снятие направления пользователем.
5. Проверка `UNIQUE(study_date)`; при существующем подтверждении — TRIP-09 (ручные поездки даты сохраняются).
6. Резолшн тарифов по ALG-09 на `ride_date` и ступени по ALG-02; неразрешённый базовый тариф → блокировка (TRIP-19).
7. Подтверждение.
8. В одной транзакции: подтверждение, поездки по каждому рейсу, стоимость и экономия (FARE-09/FARE-10), границы периода и номера (ALG-02, ALG-03), снапшот типа недели (CONF-04), каскадный пересчёт (CALC-04), пересчёт остатка.
9. Обновление виджетов и журнала; показ итога пересчёта (CALC-04).

### ALG-07. Остаток кошелька `[О]`

`остаток = Σ(topup.amount − topup.fee) − Σ(rides.paid_price, payment_method = strelka)` по всем датам `<= ride_date`. Предупреждение — по WAL-05 (не показывается до первого пополнения).

### ALG-09. Резолшн тарифа `[О]`

1. Вход: `kind`, `date` (обычно `ride_date`).
2. Среди активных тарифов вида `kind` выбрать действующий на `date` (`effective_from <= date <= effective_to`, `effective_to IS NULL` = бессрочно).
3. Найден — его цена. Не найден: для льготных видов — FARE-10 (откат к базовому, экономия 0); для базовых видов — ошибка подтверждения (TRIP-19) с предложением задать тариф.
4. Пересечение двух действующих тарифов одного вида на дату — состояние недопустимо (FARE-02), выявляется при сохранении.
5. Для `strelka_stage1` / `strelka_stage2` выбор ступени — по ALG-02 шаг 9, затем определение цены по дате.

### ALG-10. Сиротские оверрайды `[О]`

1. После каждого сохранения редактора сетки (§9.2) для каждого оверрайда проверяется существование занятия в шаблоне по ключу `(profile_id, week_type, slot_no)`. В v1.1 к ключу добавится `group_mark`.
   **Область проверки в MVP.** Редактор сетки показывает одну неделю (тот тип, который открыт), и проверка сирот выполняется в его пределах: `week_type` берётся из открытого редактора, а не из даты каждого оверрайда. Поэтому редактор верхней недели сообщит о сиротах только среди оверрайдов верхней недели, а оверрайды нижней недели проверит редактор нижней недели. Для карточки дня (SCH-17) тип недели каждой даты вычисляется по ALG-01 корректно. Расхождение осознанное: при `cycle_length = 2` пользователь проходит обе недели, и каждая проверяется своим редактором.
2. Если занятие удалено или очищено, а оверрайд не типа `add` — оверрайд помечается **сиротским**: в ALG-04 шаг 4 он не применяется.
3. Сиротский оверрайд отображается в карточке дня предупреждением (SCH-19) с действием «Удалить изменение». После удаления слот снова показывает занятие из шаблона — отдельное действие «Вернуть занятие из шаблона» в MVP не требуется (см. SCH-19).
4. Оверрайд типа `add` сиротым не считается: он существует независимо от шаблона.
5. Массовое удаление сиротских оверрайдов — одной кнопкой, без подтверждения: удаляются все сироты сразу. Число затронутых строк пишется в журнал, список затрагиваемых дат пользователю не показывается. Если нужен выборочный контроль, сироты удаляют по одному из карточки дня (SCH-19).
6. Сиротство — производственное состояние, отдельного столбца в схеме не требует: вычисляется при чтении.

- `[У-4]` **— ОТМЕНЁН в v1.9.** Прежнее «подгруппы отображаются обе, без определения „чья неделя“» перенесено в v1.1 целиком: в MVP подгрупп нет (TPL-02…04).
- `[У-19]` Пометки дня и альтернативная пятница вынесены в v1.1 (MARK-01…05, TPL-05). В MVP отмена одной пары — оверрайдом `cancel` (§10.2), отмена диапазона дат — периодом `vacation`/`holiday`; профиль звонков всегда `default`.

- `[У-8]` Место производственной практики может быть неизвестно и уточняться позже (v1.1).
- `[У-9]` Порог `strelka_first_limit` (35) — одно значение без срока действия; сами цены — с сроками.
- `[У-10]` Учебная практика — ярлык-период без отмены занятий; её расписание вносится редактором сетки и оверрайдами до появления TODO-14 (v1.1).
- `[У-11]` Остаток кошелька достоверен только после внесения первого пополнения (WAL-09).
- `[У-12]` Глобальные правки расписания — только редактором сетки (§9.2); массового импорта и версионности шаблона недели в MVP нет.
- `[У-13]` Электричка оплачивается только студенческим билетом: «Стрелка» на пригородном поезде в модели отсутствует, скидка «Копилка» на поезд не накапливается (RT-17, FARE-03). Фиксируется в `README` (DOC-02), чтобы не выглядела упущением.
- `[У-14]` Скидка «Стрелки» — ровно две ступени; значения подтверждены пользователем (Прил. А.8, TODO-20 — ссылка на тарифный источник).
- `[У-15]` Пустые слоты не показываются в дне расписания, но показываются в редакторе сетки (SCH-03, GRID-01).
- `[У-16]` Лишняя поездка в день с окнами вносится ручной записью в журнале (REP-14), отдельного интерфейса нет.
- `[У-17]` Все автобусные маршруты имеют **единую** базовую цену `bus_base`: номер рейса в модели на цену не влияет (FARE-04). Подтверждено пользователем (волна 9). Если окажется, что пригородный маршрут (например №35) тарифицируется иначе, действует резервный механизм FARE-14.
- `[У-18]` Электричка считается **незональной**: одна цена `train_base` / `train_student` на весь участок (FARE-01). Пользователь точного ответа не дал (волна 9), поэтому в `tariffs` резервируется поле `vehicle` (NULL = «для всех»), а полноценная тарификация по номеру/участку отнесена в v1.1 (FARE-14). До тех пор отчёты по электричке корректны только для постоянного участка.
- `[У-21]` **Групповых операций редактора сетки в MVP нет** (GRID-04 → v1.1): доступны выбор предмета в ячейке и очистка одной ячейки. Следствие: смена группы или ввод расписания с нуля выполняется по ячейкам (FIRST-11, FIRST-16) — это медленнее, но не требует отдельных алгоритмов и не создаёт риска «залить не тот столбец». Отказ от ввода расписания при первом запуске обратим кнопкой «Вернуть стартовый набор недели» (GRID-11).
- `[У-22]` **Переноса пары в MVP нет** (OVR-06 → v1.1): типы оверрайдов — `cancel`, `replace`, `add`. Перенос выражается двумя действиями: `cancel` на исходном слоте и `add` в свободный целевой. Флаг `keep_original` (оставить копию в исходном слоте) недоступен до v1.1. Статус «Перенесено» в MVP не выставляется, но остаётся в перечислении статусов для совместимости со схемой.
- `[У-23]` **Режимов «шаблон верхней» и «шаблон нижней недели» в расписании нет** (SCH-02): расписание показывает только конкретные даты — текущую неделю, следующую или выбранную. Шаблон как таковой смотрят и правят в редакторе сетки (§9.2), поэтому отдельный режим дублировал бы его без возможности правки.

## 35. Возможные улучшения — план развития

План развития продукта не является требованием MVP. Всё, что вынесено за пределы MVP, перечислено в §34.1 (`NFR-08`) и §34.2 (`[У-*]`): там указано, что именно относится к v1.1, что к v1.2 и что не требуется вовсе. Отдельного документа с планом развития в комплекте поставки нет.

Ориентиры по версиям:

- **v1.1** — пометки дня (`MARK-01`…`MARK-05`) и альтернативная пятница (`TPL-05`); подгруппы (`group_mark`); учебная и производственная практика и экзаменационная сессия как виды периодов; модуль экзаменов (`EXAM-01`…`EXAM-12`); перенос пары (`move`, `OVR-06`); групповые операции редактора сетки (`GRID-04`); редактирование блоков звонков (`BELL-13`…`BELL-17`); правка и удаление тарифов; диапазон дат в фильтрах; бейджи и индикатор длительных операций; переопределение маршрута на период (`TRIP-17`).
- **v1.2** — многоступенчатая шкала скидки (`TODO-9`); импорт сетки недели из файла (`FIRST-13`); цикл длиннее двух недель (`TODO-15`); автоподбор поездок по расписанию и расчёт времени выхода.
- **вне плана** — синхронизация с интернетом, многопользовательский режим, экспорт и импорт данных, автоматическое резервное копирование, механизм автомиграций схемы, системные уведомления.

Нумерация последующих разделов сохранена, поэтому ссылки `§36`/`§37` остаются действительными.

## 36. Сценарии использования

Сценарии, помеченные в версии 1.10 как *(v1.1)* (альтернативная пятница, учебная и производственная практика, экзаменационная сессия, подгруппы), в MVP недоступны; их состав перечислен в §34.1. Нумерация сохранённых сценариев **не сжимается**: номера привязаны к проверкам слоя 3 Прил. В.

**36.1. Просмотр расписания на сегодня.** Открыть приложение → дата, тип недели, период (если есть) → «Расписание» → занятия с учётом периодов и оверрайдов (ALG-04). Пустые слоты не показываются (SCH-03).

**36.2. Отмена пары.** Открыть дату → блок → «Отменить» → статус «Отменено» → шаблон не изменён.

**36.4. Начало каникул.** «Настройки → Календарь» → период `vacation` (`no_classes = 1`) → расписание показывает «Каникулы» → поездки доступны вручную, автоподстановка не выполняется.

**36.5. Смена чередования после каникул.** «Расписание» → «Изменить чередование недель…» → открывается «Настройки → Недели» → правится опорная дата и тип действующего якоря (или добавляется новый с датой действия) → прошлые даты сохраняют прежний тип, если новый якорь заведён отдельно (ALG-01, WEEK-05, WEEK-06).

**36.9. Подтверждение поездок дня.** Виджет «Поездки на сегодня» → «Поездки» → вкладка подтверждения → выбрать шаблоны «Туда» и «Обратно» → окно показывает дату, направления, число рейсов, предварительную стоимость и экономию → «Проверить стоимость» выводит номер до/после, границы периода и остаток → «Подтвердить» → поездки в журнале.

**36.10. Изменение способа оплаты.** Журнал → поездка → «Стрелка → дебетовая карта» → стоимость по `bus_base` на `ride_date` → каскадный пересчёт CALC-04 (все последующие номера и ступени) → итог показан пользователю.

**36.11. Пополнение «Стрелки».** «Расходы» → журнал пополнений → «Добавить» → дата и сумма → остаток и предупреждение обновились. Первый ввод — по WAL-09 с комментарием «начальный остаток».

**36.12. Истечение льготы.** Дата после конца действия `train_student` → ALG-09 откатывает к `train_base` → в подтверждении дня бейдж «Льгота не действует», экономия 0 → поездка сохраняется по полной цене, счётчик растёт.

**36.14. Быстрый ввод.** На ходу: журнал пополнений → «Добавить» → дата и сумма → Enter → остаток обновился.

**36.15. Первый запуск на чистой машине.** `install.bat` → `start.bat` → БД в `%APPDATA%` → стартовый набор загружен → **запрос имени и группы (FIRST-15, отказ допустим)** → **предложение ввести расписание пары недели (FIRST-16)**: ввод по ячейкам с завершением «Готово», либо кнопка «По умолчанию» — стартовый набор остаётся нетронутым → предложение ввести начальный остаток «Стрелки» → предложение указать номер поездки на карте (FIRST-14, отказ допустим) → главный экран с расписанием на сегодня и подставленными шаблонами.

**36.16. Правка расписания на новый семестр.** «Расписание» → «Редактировать сетку недели…» → верхняя неделя → по ячейкам: Пн слот 2 → «МДК.01.01», слот 3 → «Компьютерные сети» … → каждая правка сохраняется немедленно → существующие оверрайды дат не удалены, ставшие сиротами показаны предупреждением (ALG-10, SCH-19). Групповых операций нет (`[У-21]`), поэтому вся неделя вводится по одной ячейке.

**36.17. Первый запуск для другой группы.** Приложение запущено, стартовый набор загружен → «Настройки → Предметы» → добавить свои предметы (SUBJ-04), при необходимости отключив лишние из стартового набора → «Расписание» → «Редактировать сетку недели…» → нижняя неделя → очищать ячейки по одной (GRID-05; «очистить неделю» — v1.1) → заполнить своими предметами (GRID-02: выбор из списка или набор названия) → повторить для верхней недели → расписание готово без участия разработчика (FIRST-11). Если набор испорчен, кнопка «Вернуть стартовый набор недели» (GRID-11) восстанавливает неделю из Прил. А.3.

**36.18. Окна и поездка домой среди дня.** Учебный день с окнами: студент уезжает домой и возвращается вечером. «Расходы» → «Добавить поездку» (REP-14) → направление, транспорт, способ оплаты → поездка создаётся с `is_manual = 1`, увеличивает счётчик и уменьшает остаток → при вечернем подтверждении дня ручная поездка **не удаляется** (TRIP-09, TRIP-10).

**36.19. Болезнь две недели.** Студент отсутствовал 14 дней, следующая поездка — через 32 дня после последней. ALG-02 шаг 4, ветвь `next <= D` (поездка 15.11 сама открывает новый период): номер 1, ступень — первая. Никаких ручных действий не требуется.

**36.20. Домашнее задание со слов преподавателя.** На паре преподаватель называет задание → «Домашние задания» → «Добавить» → предмет, дата сдачи, описание → Enter (≤ 3 поля, HW-07) → задание появляется в виджете «Домашние задания» (UI-10) и меткой в мини-календаре (UI-05) → на паре того же предмета в день сдачи виден бейдж (HW-06) → по выполнении флажок в списке переводит статус в `done`, просроченные активные задания выделены отдельной группой (HW-08, HW-15).

**36.21. Отмена пары и замена без переноса.** Преподаватель заболел: «Расписание» → дата → слот → «Отменить» (OVR-04) → соседние пары не смещаются, статус «Отменено». Если пару ведёт другой преподаватель — «Заменить» (OVR-05). Если занятие нужно перенести на другое время, в MVP это два действия: «Отменить» на исходном слоте и «Добавить» в свободный целевой (`[У-22]`); тип `move` появится в v1.1.

## 37. Корректность данных, ошибки, открытые вопросы

### 37.1. Корректность

- `[О]` DATA-11 — дата корректна; некорректная не сохраняется.
- `[О]` DATA-12 — время в пределах суток, `ЧЧ:ММ`.
- `[О]` DATA-13 — суммы `Decimal`, 2 знака, `ROUND_HALF_UP`.
- `[О]` DATA-14 — в счётчик «Стрелки» входят только `strelka`; `debit_card` и `train_student` не влияют (RT-17).
- `[О]` DATA-15 — ссылочная целостность внешними ключами; удаление используемой сущности блокируется или заменяется деактивацией.
- `[О]` DATA-16 — изменение звонков, тарифов, шаблонов (включая правки редактором), периодов и рейсов дня не изменяет ранее созданные поездки, **кроме** явного CALC-04. **Отдельно:** скользящие периоды (ALG-02) делают изменение истории `strelka`-поездок законным основанием пересчитать **будущие** поездки — это не нарушение снапшотов, а следствие модели; снапшоты прошлых (ранее затронутой даты) поездок при этом не меняются.
- `[О]` DATA-17 — диапазоны периодов и профилей непротиворечивы: `date_from <= date_to`, `effective_from < effective_to`.
- `[О]` DATA-18 — якоря недели: `effective_from` уникален; тарифы одного вида: пересечений действий нет (FARE-02).
- `[О]` DATA-20 — редактор сетки: сохранение ячейки атомарно; очистка ячейки удаляет только строку шаблона, не трогая слот, части и оверрайды (GRID-05, ALG-10).
- `[О]` DATA-21 — `strelka_initial_ride_count >= 0`; `strelka_period_anchor_date`, если задана (не пустая строка), — корректная дата **не позже сегодня**; раньше самой ранней поездки она задаваться **может** (случай «период на карте начался до начала учёта», ALG-02 шаг 2); нарушение — отказ сохранения с сообщением (FARE-12).

### 37.2. Обработка ошибок

| Ситуация | Поведение `[О]` ERR |
|---|---|
| БД занята другим процессом | «База данных занята», повтор через 1 с до 5 попыток, затем предложить закрыть экземпляр |
| Нет прав на запись в каталог БД | Предложить другой путь; при отказе — режим только для чтения с баннером |
| Каталог из настроек не существует (перенос БД на другую машину или переименование профиля) | Не ошибка запуска: сообщение и предложение указать новый путь в UI; данные доступны на чтение (GEN-16, DATA-06) |
| БД повреждена | Предложить новую или восстановить из копии; старая переименовывается, не удаляется |
| Версия схемы не совпадает (выше или ниже) | Отказ старта с сообщением; файл не изменяется (DATA-19) |
| Тариф не разрешается на дату поездки | Блокировка подтверждения, переход к редактору тарифов (TRIP-19) |
| `strelka_period_anchor_date` позже сегодняшней даты | Отказ сохранения с объяснением (DATA-21). Значение **раньше** первой поездки — нормально (ALG-02, самокоррекция устаревшего якоря) |
| Каскадный пересчёт изменяет более 500 записей | Подтверждение с указанием количества и суммы (CALC-04) |
| Сиротский оверрайд после правки сетки | Предупреждение в карточке дня, оверрайд не применяется, действия по ALG-10 |
| Некорректный ввод в форме | Валидация до сохранения, подсветка поля, форма не закрывается |
| Ошибка в транзакции | Откат, сообщение, запись в `logs`, данные в прежнем состоянии |
| Нет Python в `install.bat` | Явное сообщение, окно не закрывается |
| Удаление используемой сущности | Предупреждение с количеством ссылок и предложение деактивации |
| Перекрывающиеся якорь, тариф или период | Сообщение с конфликтующими записями, сохранение отклонено |
| Дата внутри периода без занятий | Кнопка подтверждения поездок активна, автоподстановка не выполняется |

### А.4.1. Ожидаемая нагрузка на счётчик (справочно, для приёмки слоя 2)

Для базового маршрута «Электричка + №22» в обе стороны засчитывается **2 поездки в день**: автобус туда и обратно; электричка счётчик не увеличивает (RT-17, `[У-13]`, CALC-02). Сколько учебных дней попадает в 30-дневное скользящее окно, зависит от графика недели и от производственного календаря (праздники, переносы, каникулы). Приблизительная оценка для постоянного графика:

| График | Учебных дней в окне | Поездок за период | Где проходится порог 35 | Вторая ступень |
|---|---|---|---|---|
| Пн–Пт | ~22 | ~44 | на 18-м **учебном дне** (поездки 35 и 36) | 36…44 — 9 поездок |
| Пн–Сб (стартовый набор, А.3) | ~26 | ~52 | на 18-м **учебном дне** (поездки 35 и 36) | 36…52 — 17 поездок |

**Числа в таблице — порядок величины, а не расчёт по календарю 2026:** точное число учебных дней в конкретном окне зависит от праздников и переносов, которых в стартовом наборе нет (А.5), и пользователь вносит их сам (`[У-5]`). Слой 2 (ACC-S-19) проверяет только сам факт прохождения порога 35 внутри одного периода, а не точное число поездок. Механика нумерации проверяется слоем 1 на синтетических фикстурах (TEST-01, ACC-M-83, ACC-M-93), где число дней задаётся фикстурой явно.

### А.7. Ожидаемое поведение редактора сетки на стартовом наборе

Значения для слоя 2 приёмки (Прил. В, ACC-S-11…ACC-S-14):

Групповой операции «Очистить неделю» (GRID-04) в MVP **нет** — она отнесена к v1.1 (§34.1 п. 31), поэтому удаление всех 16 строк сразу недоступно; для этого служит «Вернуть стартовый набор недели» (GRID-11) — но она восстанавливает набор, а не очищает его.

5. **Страница расписания** (не редактор) на той же верхней неделе показывает только заполненные слоты: Пн 3 строки, Вт 3, Ср 2, Чт 3, Пт 2, Сб 3 — без пустых строк 4 и 5 (SCH-03, `[У-15]`).

## Приложение Б. Схема базы данных

```sql
-- К ТЗ «Студенческий органайзер» v1.13 (документ: TZ-MVP.md)
--
-- Соглашения:
--   время  — TEXT 'ЧЧ:ММ'
--   даты   — TEXT 'ГГГГ-ММ-ДД'
--   суммы  — NUMERIC (на уровне приложения — Decimal, 2 знака, ROUND_HALF_UP)
--   NULL в effective_to / date_to / period_start_date — «не задано»
-- Имена таблиц и полей могут быть изменены при сохранении смысла (§30 ТЗ).
-- Версия схемы: 1 (ключ settings.schema_version).
-- Любое несовпадение версии при открытии (выше ИЛИ ниже) — отказ старта,
-- файл не изменяется (DATA-19). Механизм миграции — v1.1.
--
-- Схема НЕ сокращена вместе с MVP: столбцы и таблицы будущих версий присутствуют,
-- но приложение MVP их не заполняет и по ним не фильтрует. Перечень резерва —
-- относится к v1.1 (см. §34.1).
--
-- ---------------------------------------------------------------------------
-- Б.1. Настройки (ключи — реестр §30 основного документа)
-- ---------------------------------------------------------------------------
CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- Обязательные ключи стартового набора (А.0):
--   schema_version = 1
--   strelka_initial_ride_count = 0
--   strelka_period_anchor_date = ''   (ПУСТАЯ СТРОКА = «не задано»)
-- value объявлен NOT NULL, поэтому NULL-значение реестра (§30) хранится как
-- пустая строка и интерпретируется приложением как «не задано». Иные
-- представления отсутствия значения ('NULL', '0000-00-00') — ошибка валидации.
-- Валидация FARE-12 / DATA-21 — на стороне приложения:
--   strelka_initial_ride_count >= 0;
--   strelka_period_anchor_date, если задана (не пустая строка), — корректная
--   дата НЕ ПОЗЖЕ сегодня. Раньше самой ранней поездки — ДОПУСКАЕТСЯ: это
--   штатный случай «расчётный период на карте начался до начала учёта».
--   Устаревший (слишком ранний) якорь самокорректируется по ALG-02 шагу 4.
--   Изменение любого из двух ключей запускает полный каскадный пересчёт
--   (CALC-04).

-- ---------------------------------------------------------------------------
-- Б.2. Предметы
-- ---------------------------------------------------------------------------
CREATE TABLE subjects (
  id        INTEGER PRIMARY KEY,
  code      TEXT,
  name      TEXT NOT NULL,
  teacher   TEXT,
  room      TEXT,
  color     TEXT,
  is_active INTEGER NOT NULL DEFAULT 1,
  UNIQUE (code, name)                       -- SUBJ-02: одинаковый код допустим
);
-- SUBJ-05: запись создаётся в справочнике «Настройки → Предметы»; ядро
-- GridService.create_subject_for_cell готово к v1.1, но UI его не вызывает.

-- ---------------------------------------------------------------------------
-- Б.3. Тарифы (FARE-01…FARE-14, ALG-09)
-- ---------------------------------------------------------------------------
CREATE TABLE tariffs (
  id             INTEGER PRIMARY KEY,
  kind           TEXT NOT NULL CHECK (kind IN
                   ('train_base','train_student','bus_base',
                    'strelka_stage1','strelka_stage2')),
  price          NUMERIC NOT NULL CHECK (price >= 0),
  effective_from TEXT NOT NULL,
  effective_to   TEXT,                      -- NULL = бессрочно
  vehicle        TEXT,                      -- РЕЗЕРВ (FARE-14, [У-18]): NULL =
                                            -- «для всех маршрутов/участков».
                                            -- В MVP всегда NULL (FARE-04, [У-17]).
  is_active      INTEGER NOT NULL DEFAULT 1,
  comment        TEXT,
  CHECK (effective_to IS NULL OR effective_from <= effective_to)
);
-- FARE-02 / DATA-18: два АКТИВНЫХ тарифа одного kind не могут перекрывать
-- одну дату. Контроль — на стороне приложения при сохранении:
--   SELECT 1 FROM tariffs t2
--   WHERE t2.id <> :id AND t2.kind = :kind AND t2.is_active = 1
--     AND t2.vehicle IS :vehicle
--     AND t2.effective_from <= COALESCE(:to, '9999-12-31')
--     AND COALESCE(t2.effective_to, '9999-12-31') >= :from;
-- MVP: `vehicle` всегда NULL. ALG-09 выбирает тариф по (kind, ride_date);
-- фильтра по vehicle нет. В v1.1 (FARE-14) поиск становится двухпроходным:
-- сначала тариф с совпадающим `vehicle`, иначе — с `vehicle IS NULL`.
-- Поле введено сейчас, чтобы v1.1 не потребовала миграции данных ([У-18]).
-- Порог strelka_first_limit (35) здесь НЕ хранится — настройка ([У-9]).
-- Число ступеней фиксировано двумя (FARE-07); таблица ступеней — v1.2 (TODO-9).

-- ---------------------------------------------------------------------------
-- Б.4. Профили звонков (BELL-01…BELL-20)
-- ---------------------------------------------------------------------------
CREATE TABLE bell_profiles (
  id             INTEGER PRIMARY KEY,
  weekday        INTEGER NOT NULL CHECK (weekday BETWEEN 1 AND 7),  -- 1 = Пн
  variant        TEXT NOT NULL CHECK (variant IN ('default','friday_class_hour','custom')),
  name           TEXT NOT NULL,
  effective_from TEXT,                      -- NULL = бессрочно с начала
  effective_to   TEXT,                      -- NULL = без конца
  is_active      INTEGER NOT NULL DEFAULT 1,
  UNIQUE (weekday, variant, effective_from)
);
-- BELL-18: для (weekday, date) выбирается профиль, чей диапазон содержит date;
-- при отсутствии — ближайший предыдущий по effective_from.

-- ---------------------------------------------------------------------------
-- Б.5. Блоки профиля (время не хранится — только в частях, BELL-06)
-- ---------------------------------------------------------------------------
CREATE TABLE bell_slots (
  id           INTEGER PRIMARY KEY,
  profile_id   INTEGER NOT NULL REFERENCES bell_profiles(id) ON DELETE CASCADE,
  slot_no      INTEGER NOT NULL,
  pair_no      INTEGER,                     -- NULL для классного часа
  block_type   TEXT NOT NULL CHECK (block_type IN ('class_hour','pair','custom')),
  display_name TEXT,
  sort_order   INTEGER,
  UNIQUE (profile_id, slot_no)
);
-- GRID-05: редактор недельной сетки НЕ трогает эту таблицу.
-- BELL-13/BELL-16: добавление — только в конец; вставка в середину запрещена,
-- пока на slot_no есть ссылки из schedule_templates или schedule_overrides.
-- SCH-03: слоты без занятия и без оверрайда не показываются в дне расписания,
-- но показываются в редакторе (GRID-01).

-- ---------------------------------------------------------------------------
-- Б.6. Части блоков
-- ---------------------------------------------------------------------------
CREATE TABLE bell_slot_parts (
  id         INTEGER PRIMARY KEY,
  slot_id    INTEGER NOT NULL REFERENCES bell_slots(id) ON DELETE CASCADE,
  seq        INTEGER NOT NULL,
  part_type  TEXT NOT NULL CHECK (part_type IN ('lesson','break')),
  start_time TEXT NOT NULL,
  end_time   TEXT NOT NULL,
  UNIQUE (slot_id, seq)
);
-- BELL-17 (контроль приложения): start_time < end_time; части одного слота
-- и блоки профиля не пересекаются; первая и последняя часть — lesson.

-- ---------------------------------------------------------------------------
-- Б.7. Шаблоны расписания (TPL-01…TPL-08, GRID-01…GRID-08)
-- ---------------------------------------------------------------------------
CREATE TABLE schedule_templates (
  id             INTEGER PRIMARY KEY,
  profile_id     INTEGER NOT NULL REFERENCES bell_profiles(id),
  week_type      TEXT NOT NULL CHECK (week_type IN ('upper','lower')),
  slot_no        INTEGER NOT NULL,
  group_mark     INTEGER CHECK (group_mark IN (1, 2)),   -- NULL = общее занятие.
                                                         -- РЕЗЕРВ v1.1 (TPL-02):
                                                         -- в MVP всегда NULL
  subject_id     INTEGER REFERENCES subjects(id),        -- NULL — занятия нет
                                                         -- (надгробие, TPL-08)
  effective_from TEXT NOT NULL,                          -- TPL-08: с какой даты
                                                         -- действует версия
  UNIQUE (profile_id, week_type, slot_no, group_mark, effective_from)
);
-- TPL-01/TPL-08 (MVP): строка — версия позиции, действующая с effective_from
--   до начала следующей версии той же позиции. Стартовый набор пишется
--   с effective_from = '0001-01-01'; правка из редактора — с выбранной даты.
-- GRID-02: сохранение ячейки = удаление перекрытых версий (effective_from >=
--   выбранной даты) и вставка новой (DATA-20).
-- GRID-05/TPL-08: очистка с даты = удаление перекрытых версий и вставка
--   надгробия (subject_id IS NULL), только если раньше было что скрывать.
-- GRID-04 «очистить день/неделю» = DELETE строк шаблона, слоты остаются.
-- ALG-10: удаление строки делает связанные оверрайды сиротскими,
--         но сами оверрайды НЕ удаляет (OVR-12); сиротство считается по
--         версии, действующей на дату оверрайда.
-- Внешний ключ на bell_slots не вводится намеренно: slot_no — логический ключ,
-- его валидность проверяет приложение (BELL-16 защищает от рассогласования).

-- ---------------------------------------------------------------------------
-- Б.8. Разовые изменения расписания (OVR-01…OVR-12)
-- ---------------------------------------------------------------------------
CREATE TABLE schedule_overrides (
  id              INTEGER PRIMARY KEY,
  date            TEXT NOT NULL,
  profile_id      INTEGER NOT NULL REFERENCES bell_profiles(id),
  slot_no         INTEGER NOT NULL,
  group_mark      INTEGER CHECK (group_mark IN (1, 2)),  -- РЕЗЕРВ v1.1, MVP: NULL
  part_seq        INTEGER,                  -- зарезервировано для v1.2 (OVR-09)
  override_type   TEXT NOT NULL CHECK (override_type IN ('cancel','replace','add','move')),
  subject_id      INTEGER REFERENCES subjects(id),
  teacher         TEXT,
  room            TEXT,
  custom_start    TEXT,
  custom_end      TEXT,
  target_slot_no  INTEGER,
  keep_original   INTEGER NOT NULL DEFAULT 0,
  comment         TEXT,
  created_at      TEXT NOT NULL
);
-- OVR-08 (контроль приложения). MVP (без подгрупп): не более одного оверрайда
-- из cancel/replace/move на (date, profile_id, slot_no); add в занятый слот
-- запрещён. v1.1 добавляет в ключ group_mark — столбец уже есть.
-- ALG-10: сиротство — ПРОИЗВОДНОЕ состояние, отдельного столбца нет.
-- Вычисляется при чтении: override_type <> 'add' И в schedule_templates нет
-- строки (profile_id, week_type даты по ALG-01, slot_no[, group_mark в v1.1]).

-- ---------------------------------------------------------------------------
-- Б.9. Учебные периоды (CAL-01…CAL-14)
-- MVP: kinds 'vacation' и 'holiday' (CAL-02). Остальные виды, place и
-- переопределения маршрута — РЕЗЕРВ v1.1 (CAL-05…CAL-08, TRIP-17); CHECK
-- намеренно допускает их, чтобы возврат функций не требовал миграции.
-- ---------------------------------------------------------------------------
CREATE TABLE study_periods (
  id                   INTEGER PRIMARY KEY,
  kind                 TEXT NOT NULL CHECK (kind IN
                         ('vacation','holiday','practice_educational',
                          'practice_industrial','exam_session')),

-- Удаление предмета, на который ссылаются задания, запрещено (HW-09):
```
